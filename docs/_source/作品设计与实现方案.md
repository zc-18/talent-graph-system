## 一、项目背景与痛点

在国家从"人口红利"向"人才红利"转型的关键期，"新质生产力""人工智能+"与数字经济推动以新一代信息技术为代表的新兴领域快速发展，技术迭代速度远超人才培养周期，劳动力市场出现严重"结构性矛盾"：

- **企业侧**："招不到合适的人"，人岗匹配度低、新兴岗位识别难，招聘与培养成本高；
- **人才侧**：新兴领域青年职业路径模糊、技能需求动态性强，缺乏动态行业技能图谱指引；
- **方法侧**：传统人才盘点依赖关键词匹配，对技术趋势无实时感知，难以回答"技术 A 的爆发会给岗位 B 带来哪些新技能需求"。

更深层的数据难题在于：招聘 JD（Job Description）普遍存在 **时滞（lag）、噪音（noise）、抄袭（plagiarism）、能力通胀（inflation）**；同时大模型在生成能力定义时存在 **"幻觉"** 风险，直接生成的岗位能力不可信、不可溯源。

**本系统的目标**：以"数据驱动 + 大模型 + 知识图谱"为核心，构建一个能够自我进化的"人才能力大脑"，实现从"静态画像"到"动态感知"的跨越，形成 **"多源数据采集 → 新岗位发现与定义 / 既有岗位能力更新 → 能力图谱动态构建 → 简历解析 → 精准匹配与差距分析 → 改进建议与学习路径"** 的全流程闭环。

## 二、系统总体设计

### 2.1 全流程闭环

```
①多源数据采集             ②清洗·交叉验证         ③大模型结构化抽取
 官网JD/政府平台/数据集  →  去抄袭/通胀/时滞/噪音  →  JD解析(职责·粗/细粒度技能)
        ▲                                                      │
        │  人工反馈回流（人工优化/能力项增删改 → 演化记录）        ▼
⑥人岗匹配与诊断   ◀──   ⑤图谱构建与动态演化   ◀──   ④反幻觉交叉验证聚合
 简历解析·多维匹配         岗位-技能点知识图谱        统一置信度公式 + 证据溯源
 差距分析·学习路径         版本演化+级别演化追踪       过滤低置信"幻觉"能力项
```

闭环的关键在两端相接：应用层（岗位库管理）的人工优化通过 `manual-edit` 写回演化记录（⑥→②/⑤），采集台账（`crawl_batch`）与漏斗统计在首页可视化，使"采集→清洗→图谱→演化→应用→反馈"每一环都有真实数字可查。当前全流程漏斗为：**采集 2523 条 → SimHash 去重后 2359 条 → 全部解析 2359 条 → 交叉验证确认能力 920 条 / 单来源降级候选 1885 条 → 沉淀为 32 个岗位、4570 项技能**。

**采集护栏（代码级强制，`collect/base.py`）**：robots.txt 逐 host 检查、单站 ≥4 秒控频 + 随机抖动、不携带任何登录态、不采任何个人信息（字段名 `phone|email|wechat|联系人` 直接抛错拦截 + 正文正则打码）、每次请求写一行台账日志。**每条 JD 均可溯源**：本地 jsonl 原始留存 + `manifest.json` + `crawl_log.jsonl`，数据库 `raw_jd` 表记录平台/公司/原始 URL/发布时间/采集批次，`crawl_batch` 表记录批次台账（首页「数据源台账」直读）。

**飞书招聘 SaaS 官网的合规依据（本轮新增源，需特别说明）**：这批站点是企业把自己的官方招聘官网托管在飞书招聘 SaaS 上（域名形如 `{企业}.jobs.feishu.cn`），属于**企业面向公众主动发布岗位的官方渠道**，故与腾讯/网易官网同级定为 official / 权威度 1.0。三点合规要点：①**全程无需登录**，不注册账号、不使用任何 Cookie 身份；②接口所需的 csrf token 由 `/api/v1/csrf/token` 面向所有访客（含未登录访客）公开下发，属会话卫生机制而非访问控制；③浏览器请求上携带的 `_signature` 反爬签名**我们既未复现也未绕过**——实测将该参数整个去掉后接口照常返回 200 并给出同样的公开职位数据，这恰恰说明该接口本身对公众开放。租户来源亦有据：`probe_feishu_tenants.py` 共探测 95 个候选 slug，仅采纳公开职位数 > 0 的 11 家。

| 平台 | 实测结论 | 处置 |
|---|---|---|
| BOSS直聘 | robots.txt 明确 Disallow `/*?query=*`、`*?city=*`、`*?position=*`、`*?salary=*` 等，**正是职位检索必需的查询路径** | 不采 |

## 三、核心功能实现

### 3.1 新岗位发现与定义

**新兴岗位判据（形式化定义）**：本系统认定的新兴岗位须满足以下两类判据之一，且必须有权威佐证：

- **新出现型（new）**：岗位于近两年（2025-2026 为佳）首次规模化出现于劳动力市场。佐证优先级：人社部新职业/新工种目录 > 头部机构人才报告 > 多源网络证据。
- **复兴型（revived）**：岗位曾出现、经历沉寂期、近期重新兴起（如"人工智能数字人训练师"：2021-2022 元宇宙热潮期出现→退潮→大模型驱动下复兴，人社部 2024-08 正式增设工种）。

每个新兴岗位在库中标注 `emergence_type`（new/revived）、`first_seen_date`（首次可考证出现时间）与 `authority_evidence`（权威佐证：文件标题、发布机构、日期、原文引用、链接与本地归档快照）。当前 6 个新兴岗位的佐证包括：人社部 2026-07-02 公示（"智能体开发员"工种、"具身智能机器人应用技术员""数字孪生工程技术人员"新职业）、人社部 2025-07-22 第七批新职业（"生成式人工智能系统测试员"工种）、人社部 2024-08 增设工种（"人工智能数字人训练师"），以及翰德《2025 人才趋势报告》、脉脉《2025 年 AI 人才流动报告》等头部机构报告。反向地，曾经火热但已回落为通用技能的"提示词工程师"（麦肯锡《State of AI 2025》）被系统降级为常规岗位并记录演化叙事——系统对岗位"兴起/回落/复兴"具备双向识别能力。

**目标**：识别市场上萌芽/兴起中、尚未标准化的新岗位，并生成结构化定义（岗位名称、核心职责、必备技能、加分技能、典型行业应用场景），支持人工优化与动态更新。

**实现流程**（`services/discovery.py`）：
1. **候选发现**：内置新兴岗位种子（AI 智能体开发工程师、具身智能工程师、大模型推理优化工程师等），或用户自定义关键词；
2. **权威佐证匹配**：优先匹配本地权威佐证登记表（`data/authority/`，人社部文件 + 头部机构报告，含原文快照归档），命中部委政策文件的岗位新兴度 ≥0.9、报告级 ≥0.75；
3. **多源证据采集**：Tavily + Serper.dev **两个独立来源**并行检索，按 URL 去重，统计独立来源数；近 180 天新闻检索评估"新兴度"；
4. **RAG 接地生成**：将权威佐证与检索证据作为上下文，约束大模型"只基于证据定义、禁止臆造"，生成结构化岗位定义；
5. **能力项交叉验证**：对每个生成的技能，校验其是否在证据文本中出现，按统一置信度公式打分，标注 `web_verified`；
6. **入库**：写入 `is_new=True` 的岗位节点（含 emergence_type / first_seen_date / 权威佐证），全景图谱中以琥珀色高亮。

**输入输出示例**：见 `docs/测试数据/新岗位_AI智能体开发工程师_图谱与数据源.json`（输入关键词 → 多源联网证据 → 结构化岗位定义，含核心职责、必备/加分技能、典型场景）。

### 3.2 既有岗位能力动态更新（演化）

**目标**：针对现有岗位（如 Java 开发工程师），识别能力要求变化，明确标注 **新增 / 删除 / 修改** 的能力项，提供更新说明与数据源，支持人工优化与动态演化。

**实现流程**（`services/evolution.py`）：
1. 取岗位当前能力快照（旧版本）；
2. 解析输入的最新 JD，与历史能力合并进行交叉验证聚合；
3. **差异计算**：
   - **新增（add）**：新数据中出现、旧图谱中没有的能力项，附独立来源数与置信度；
   - **删除 / 淘汰（delete）**：该能力项在**最新窗口的 JD 原文里一次都没有出现**，且原为**必备能力**，且窗口 JD 数 **≥20**（三个条件同时成立才下淘汰结论），标记 deprecated、保留历史可回溯；
   - **修改（modify）**：重要度（必备↔加分）或权重显著变化（阈值 0.2）；**或**该能力仍出现在新 JD 中、但交叉验证支持减弱而被降为候选（记作"降级为候选能力项，保留观察，未淘汰"）；
4. 每条变更记录 `reason`（更新说明）与 `data_source`（数据源，淘汰项额外记录窗口 JD 数），岗位版本号 +1，全部写入 `capability_change` 表，前端时间线展示。

> **淘汰判据的关键设计**（详见 4.3）：判定"消失"用的是**先验注入之前**最新窗口 JD 里真实出现过的技能名集合（`window_skill_names`），而不是聚合后的新能力表——因为聚合时旧能力会作为历史先验被注入，用聚合结果判淘汰在原理上就判不出来。

**真实三时间切片演化链（2018 → 2024 → 2026）**：本系统的演化不是"造一条时间线"，而是把三个**独立来源的真实语料切片**按时间顺序依次灌入同一条演化服务链：2018-12（`dataset_51job2018`）→ 2024-07（`dataset_aijob2024`）→ 2026-07（腾讯 / 网易 / 飞书 ATS / 国聘四个现网来源）。运行结果：

- **共 621 条真实变更记录**：新增 367 / 淘汰 143 / 修改 111；
- 按批次：`2024hist-r1` 批次产生 **128 条**，`2026W31` 批次产生 **493 条**；
- 版本分布：**v1 14 个岗位 / v2 9 个 / v3 6 个**；
- **15 个传统岗位**在 2018 语料中即存在，走完整演化链条；其中 **6 个 AI 族岗位**（机器学习、自然语言处理、计算机视觉、深度学习、推荐算法、嵌入式软件）在 2024 切片中亦有样本，因而拥有 2024 中间态，到 2026 演化到 **v3**；
- **另外 14 个岗位**（大模型算法、AI 智能体开发、具身智能、数字孪生、大模型推理优化、AIGC、多模态、边缘计算、自动驾驶、机器人算法、数字人、提示词工程、AI 产品、生成式 AI 测试员）在 2018 语料中**完全不存在**，只能单独建 v1 —— **这本身就是"新岗位涌现"最直接的数据证据**：不是我们宣称它们新，而是历史语料里根本找不到它们。

> **如实说明**：Java 岗那 23 项里的 **Django、Flask 属于 2018 语料的聚类污染**——这两个 Python Web 框架在建 2018 基线时被误归入 Java 岗位簇，因此它们的"淘汰"反映的是历史聚类噪声被新语料修正，而不是真实的技术退场。我们把它列出来而不是悄悄剔掉，因为它同时说明了淘汰判据本身是机械执行的、没有为了好看做人工挑选。

**分级演化（初级/中级/高级晋升路径）**（`services/leveling.py`）：在"岗位随时间演化"之外，系统还建模**岗位内部按级别的能力演化**。真实 JD 在采集入库时按标题关键词（高级/资深/专家/初级）与经验年限（0-3 年 / 3-5 年 / 5 年以上）推断级别（junior/middle/senior），按级别分桶后各自复用同一套交叉验证聚合，生成分级能力画像（`job_level_skill` 表，当前 **32 个岗位中 29 个达标、共 916 条分级能力记录**）；"中级→高级怎么演化"即两个级别画像的差异计算（复用演化 diff 引擎），输出"晋升需新增掌握 X""晋升要求强化 Y（权重 45%→72%）""Z 在高级 JD 中不再单列、视为默认前提"等晋升语义的变更项，前端以 初级→中级→高级 阶梯视图展示。

## 四、关键技术创新

### 4.1 多源异构数据清洗与交叉验证融合机制（解决时滞/噪音/抄袭/通胀）

赛题创新点①。`services/cleaning.py` + `services/ingest.py`：

| 问题 | 检测方法 | 处理 |
|------|----------|------|
| **抄袭/重复** | 精确 MD5 + **64 位 SimHash** 海明距离（阈值≤3）近似去重 | 标记 `is_duplicate`，**排除出交叉验证**，避免重复来源虚增可信度 |
| **时滞（lag）** | `publish_date` 与采集时间差 | 新鲜度指数衰减权重（半衰期 180 天），旧数据降权 |
| **噪音（noise）** | 技能同义词归一化字典 + 后缀裁剪（"微服务架构"→"微服务"） | 合并同义技能，降低噪音碎片 |
| **能力通胀（inflation）** | 单条 JD 技能数显著高于同岗位中位数（≥median×1.4 且超出≥4）**且** 非共识/冷门技能占比>35% | 标记 `inflation_flag`，通胀技能因缺乏交叉验证被自动过滤 |

**实测效果**：对抗测试夹具 379 条 JD 中，植入的 **8 条整段抄袭样本全部检出（8/8，另自动检出 3 条模板高度相似的近重复）**、**17 条能力通胀样本全部检出（17/17）**；在 **2523 条真实生产语料**上，SimHash 查重共检出 **164 条重复**（去重后有效 JD 2359 条），能力通胀检测标记 **452 条** JD。

### 4.2 能力"幻觉"防控机制（提升图谱构建科学性）

赛题创新点②，本系统最核心的创新。`services/hallucination.py`：

**核心思想**：单一来源（含大模型臆造）不可信；**只有被≥2 个独立来源交叉验证、或有外部网络证据支撑的能力项，才以高置信度进入图谱**，且每个能力项保留可溯源证据。

**置信度模型**（统一线性加权公式，`services/confidence.py`，全系统唯一）：

```
C = 0.35·支持率 + 0.20·来源多样性 + 0.15·时效性 + 0.20·来源权威度 + 0.10·外部验证
```

五个因子均归一化到 [0,1]，权重和为 1，因此 C 天然落在 [0,1]，**每一分都可拆解解释**（前端点击任意置信度徽章即可查看五因子分解条）。因子口径：

| 因子 | 权重 | 定义 |
|---|---|---|
| 支持率 | 0.35 | 提及该技能的独立 JD 数 ÷ 该岗位有效（非重复）JD 总数 |
| 来源多样性 | 0.20 | 独立招聘平台数 ÷ 3（封顶 1.0，多平台交叉印证优于单平台；封顶值按真实语料校准一次后冻结，本轮数据源扩容后**未再改动**） |
| 时效性 | 0.15 | 各来源新鲜度均值，指数衰减半衰期 180 天 |
| 来源权威度 | 0.20 | 各来源权威度均值：企业官方招聘官网/政府平台 1.0、公开数据集 0.7、网络检索 0.6 |
| 外部验证 | 0.10 | 有 Tavily/Serper 联网检索或权威文件（人社部/头部机构报告）佐证记 1，否则 0 |

**算例（口径演示）**：某岗位技能"大语言模型"被 9/13 条有效 JD 提及（支持率 0.69），来源覆盖 3 个独立平台（多样性 3/3=1.0，达到封顶），平均新鲜度 0.88，全部来自企业官网/政府平台（权威度 1.0），暂无外部检索验证（0）：
`C = 0.35×0.69 + 0.20×1.0 + 0.15×0.88 + 0.20×1.0 + 0.10×0 ≈ 0.78`。
岗位整体置信度 = 粗粒度 active 能力项的**权重加权**平均（核心必备技能主导，长尾低频加分项不拖累整体）。

**三重防控**：
1. **交叉验证门槛**：必备技能要求 ≥2 个独立非重复来源，否则自动降级为加分技能（防止单源臆造的能力项被定义为"必备"）；
2. **置信度过滤**：低于阈值（0.45）的能力项标记为 `candidate`，不进入正式图谱（过滤潜在幻觉/噪音）；
3. **证据溯源**：每个能力项保留多条证据（原始 JD 片段 / 外部链接），前端可逐项展开追溯，实现 **可解释、可审计**。

**实测**（真实语料）：构建过程中共 **920 条岗位-能力关系通过交叉验证进入正式图谱（active）**，另有 **1885 项单来源细粒度技能点被标记为 `candidate`**、保留在库可展开查看但不进入图谱主视图与匹配计算；典型如单条 JD 单独出现的冷门技术词、以及"顶会论文"这类 JD 短语碎片被自动降级。全库岗位置信度均值 **0.6167**（上一版真实语料下为 0.535）。

**必须说清楚的是：这个提升不是调参调出来的——置信度公式、五因子权重、多样性封顶值（3）与过滤阈值（0.45）全部原封未动。** 提升来自数据源本身：本轮语料从 3 个渠道扩到 5 类渠道 / 6 个平台批次后，同一技能最多可被 **5 个独立来源**交叉验证（来源池为 2018 数据集 / 2024 数据集 / 腾讯 / 网易 / 飞书 ATS / 国聘），"来源多样性"因子更容易达到封顶，且新增的两个来源（飞书 ATS 为企业官网 tier=official、国聘为国家级平台 tier=gov）权威度均为 1.0，把"来源权威度"因子的均值也整体抬高。换言之，**是证据变厚了，不是分数被调高了**——这正是交叉验证机制"数据越多、判断越可信"的预期表现。

### 4.3 演化淘汰判据的可举证化（方法论亮点：我们自己揪出的一个静默缺陷）

演化模块最初交付时，三切片跑完的结果是"**删除 0 条**"。这个数字看起来"数据没给淘汰信号"就能解释过去，但复盘时我们没有接受这个解释，而是回去读了 diff 的实现——结果发现**删除分支在原理上永远不可能触发**：

- 调用方在做新一轮交叉验证聚合时，会把**旧能力当作 `history` 先验来源注入**（这是为了让历史证据参与打分，本身是对的）；
- 于是旧能力名必然出现在聚合后的 `new_caps` 里，判据 `name not in new_caps` **恒为假**——删除分支是死代码；
- 更严重的是：如果某个旧能力在新窗口里支持不足被降级为候选，它**三个分支都进不去**——不是新增、判不出删除、也不满足"重要度/权重显著变化"，于是**变更日志里一条记录都不留、静默消失**。一个本该被记录的能力衰减事件，就这样从审计链上蒸发了。

**修复不是"调参调出来的"，而是先定判据、再看结果**（`services/evolution.py::compute_changes`）：

| 判据 | 内容 | 为什么这样定 |
|---|---|---|
| ① 证据来源换成窗口原文 | 传入 `window_skill_names`——**先验注入之前**、最新窗口 JD 里真实出现过的技能名集合；淘汰判据改为"该能力在最新 N 条 JD 中**一次都没出现**" | 用聚合结果判淘汰在原理上判不出来；改用窗口原文后，每一条淘汰都能回到具体 JD 举证 |
| ② 只判「必备能力」的消失 | 加分项的进出不作淘汰结论 | 加分项进出频繁、不同语料用词差异极大。实测把加分项计入会**一次刷出 160+ 条假"淘汰"**（Java 岗 189 条里 166 条是加分项），真信号会被彻底淹没 |
| ③ 窗口 JD 数 ≥20 才允许下淘汰结论 | 样本不足时**不判**——缺证据不等于反证 | 门槛设 10 时实测出现假阳性：只有 16 条 JD 的运维岗把 **Nginx** 判成了"淘汰"。窗口太薄时一个常用技能碰巧没被提到就会造出这种一眼被看穿的错误。提到 20 之后该假阳性消失，样本薄的窗口（运维 16 条、大数据平台 13 条）**主动放弃下结论** |
| ④ 支持减弱的记 modify，不再静默丢弃 | 仍出现在新 JD 里但被降为候选的能力，记为"降级为候选能力项，保留观察，未淘汰" | 补上第三个分支的漏洞，保证**任何能力状态变化都在变更日志里留痕**，审计链不断 |

**这条判据链是"宁可少判、不可错判"的**：③ 明确牺牲了一部分召回（样本薄的岗位一条淘汰都不出），换取每一条淘汰都站得住。修复后三切片跑出 **143 条淘汰 + 111 条修改**，其中 111 条修改里包含了此前会被静默丢弃的能力衰减事件——这些记录不是"多出来的数字"，而是**原本就该存在、被缺陷吞掉的审计记录**。

### 4.4 嵌入模型退化守卫（工程鲁棒性创新）

实践中发现 bge-small-zh 中文向量模型对 **纯英文技能名（Spark/Hive/Java/Go）返回退化向量**（不同词余弦≈1.0），会导致语义匹配把"相关但不同"误判为"等价"，掩盖真实能力缺口。

**解决方案**：语义匹配仅在"双方均含中文字符"时启用，并加 **退化守卫**（不同字符串余弦≥0.999 视为退化向量予以忽略）；英文同义词交由词典归一化处理。该守卫使 **人岗匹配分类准确率从 86.9% 提升到 100%**，体现了对大模型/向量模型局限性的工程化防控能力。

### 4.5 RAG 接地的新岗位发现

新岗位定义不依赖大模型"凭空想象"，而是 **先用 Tavily + Serper 两个独立来源检索真实证据，再让大模型基于证据生成**，并对每个技能做证据校验，从源头降低幻觉，使新兴岗位定义"有据可循"。

### 4.6 数据合规、隐私保护与伦理治理（合规方案）

能力图谱构建涉及招聘数据与个人简历，本系统将"合规"与"幻觉防控"并列为图谱科学性的两大支柱，建立覆盖数据全生命周期的治理方案：

| 维度 | 合规措施 | 落地点 |
|------|----------|--------|
| **数据来源合规** | 仅采集**公开**招聘 JD 与公开网络证据；只对无登录墙、无反爬、robots 未禁的企业官方招聘官网与国家级公共就业平台采集；**39 个候选源逐一实测后，全部聚合类招聘平台（BOSS直聘/智联/猎聘/拉勾/牛客/前程无忧/实习僧）一条数据都未采**；不复现反爬签名、不解密自定义字体、不过人机校验；联网检索经 Tavily/Serper 合规接口获取；数据最小化（只取岗位能力相关字段） | `collect/base.py`、`probe_report.json`、`clients.multi_source_search` |
| **个人信息(PII)最小化** | 简历**仅在内存中解析**用于本次匹配，**原始简历全文与姓名等 PII 一律不落库**，服务端仅留存脱敏后的技能要素用于分析；前端明示隐私声明 | `routers/match.py`、`resume.redact_for_storage`、Match 页隐私提示 |
| **可溯源 / 可审计 / 可解释** | 每个能力项保留多条证据（原始 JD 片段 / 外部链接 + 权重），前端"溯源证据"页逐项可展开追溯，满足审计要求，杜绝"黑箱"能力定义 | `Evidence` 表、`/api/jobs/{id}/evidence` |
| **人工监督(Human-in-the-loop)** | 大模型与算法的产出为**辅助建议而非最终决策**；岗位定义、能力项重要度/权重均支持人工新增/修改/删除，并记录变更人来源（`origin: manual`）与更新说明，确保人对结果负责 | `/api/jobs/manual-edit`、`capability_change` 表 |
| **公平性与偏见防控** | 匹配仅基于**技能要素**，**不采集、不使用性别/年龄/院校/籍贯等敏感特征**，避免算法歧视；多源交叉验证削弱单一来源（含历史偏见）对图谱的主导，提升公允性 | `matching.match`、`hallucination.aggregate_capabilities` |
| **大模型输出合规边界** | 低温度 + JSON 强约束 + "禁止臆造"提示工程；所有自动生成的能力项均标注**置信度**与证据，低置信项不进入正式图谱；输出定位为"建议性"，重大用途需人工复核 | `extraction.py`、`discovery.py` |
| **数据安全** | 数据库访问受凭据保护，API Key 通过环境变量注入、不入代码库（`.env` 已 gitignore）；上传文件大小与类型校验，防止滥用 | `config.py`、`.gitignore`、`routers/match.py` |

> **合规与幻觉防控的协同**：交叉验证（多源）既是反幻觉手段，也是反"数据偏见/抄袭通胀"的合规手段；证据溯源既支撑可解释，也支撑可审计。二者共同保证图谱"可信、可查、可问责"。

## 八、总结与展望

本系统完整实现了赛题要求的全流程闭环，在 **多源交叉验证清洗** 与 **能力幻觉防控** 两大创新点上提出了可量化、可溯源的工程方案，三项核心指标均显著超过 90% 的达标线，并已稳定部署上线。

**方法论局限（如实说明）**：三个时间切片的**来源丰富度并不对等**——2018 与 2024 两个切片各自**只有单一公开数据集来源**，交叉验证机制在这两个切片上天然拿不到"多源支持"，因而它们确认下来的能力项偏少；而 2026 切片有腾讯 / 网易 / 飞书 ATS / 国聘四个独立来源。这直接导致演化变更绝大多数落在 2026 这一步（**493 / 621 条**），**其中一部分来自来源丰富度的提升，而非纯粹的岗位能力增长**。同理，淘汰判据虽然要求"最新窗口 JD 原文中一次未出现"，但窗口本身的**语料用词偏好**仍会影响结果——Java 岗 23 项淘汰中的 Django / Flask 就是 2018 语料聚类污染被新语料修正，而非真实技术退场（见 3.2）。后续若能补齐历史年份的多源语料（如更多年份的公开数据集或政府平台归档），可将这一效应从真实能力演化中剥离，得到更纯净的演化曲线。

**可迁移性**：技术方案与岗位无关，可平滑迁移到医疗、金融、智能制造等更多新一代信息技术领域岗位；数据源可扩展更多招聘平台与权威信源；图谱可对接企业人才盘点与培训体系，形成"招聘—盘点—培养"闭环。

**未来方向**：引入时间序列的技能热度趋势预测、构建岗位间转岗路径推荐、接入更强的领域向量模型以增强语义匹配、按上述局限补齐历史切片的多源语料。
