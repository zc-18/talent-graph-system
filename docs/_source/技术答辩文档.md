## 一、一句话概述

> 我们用「数据驱动 + 大模型 + 知识图谱」构建了一个可自我进化的"人才能力大脑"：从多源招聘数据中**自动发现新岗位、动态更新既有岗位能力**，构建技能点级的全景能力图谱，并对简历做**人岗匹配诊断与差距分析**；核心创新是**多源交叉验证清洗**与**能力幻觉防控**，使图谱"可信、可溯源、可演化"。

## 二、系统架构深度解析

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  前端 React+TS+ECharts （全景图谱/匹配雷达/演化时间线）        │
├─────────────────────────────────────────────────────────┤
│  API 层 FastAPI  jobs / graph / discovery / evolution / match │
├─────────────────────────────────────────────────────────┤
│  服务层（核心逻辑，与框架解耦、可单测）                          │
│   cleaning      多源清洗：SimHash去重/通胀/时滞/质量分           │
│   extraction    JD结构化解析（反幻觉提示工程）                   │
│   taxonomy      技能分类与同义词归一化（降噪）                    │
│   hallucination 交叉验证聚合 + 置信度（反幻觉核心）              │
│   discovery     新岗位发现（RAG接地）                          │
│   evolution     既有岗位能力演化（增删改）                      │
│   resume        简历解析（PDF/Word）                          │
│   matching      多维匹配/差距/学习路径                         │
│   graph_service 图谱持久化与全景查询                           │
│   ingest        数据接入编排 pipeline                         │
├─────────────────────────────────────────────────────────┤
│  外部服务  DeepSeek(LLM) · BGE(向量) · Tavily+Serper(检索)      │
│  存储      MySQL（图谱节点/关系/证据/演化/原始数据）              │
└─────────────────────────────────────────────────────────┘
```

### 2.2 数据流（端到端闭环）

`多源JD → ingest入库 → cleaning清洗去重 → extraction大模型解析 → 按岗位聚类 → hallucination交叉验证聚合（置信度+证据）→ graph_service落库 → 前端全景图谱`；
匹配链路：`简历 → resume解析 → matching对比岗位图谱 → 差距分析 → 学习路径 + 大模型改进建议`；
演化链路：`新JD → 解析聚合 → evolution与旧能力diff → 标注增删改 + 写变更记录 → 版本+1`。

## 三、核心算法详解（答辩高频考点）

### 3.1 多源数据清洗

**① 抄袭/重复检测（SimHash）**
- 对 JD 分词加权 → 每个词 MD5 映射到 64 维 → 按词频加权累加 → 符号化得 64 位指纹；
- 两条 JD 的**海明距离 ≤ 3** 判定为近似重复（抄袭），加精确 MD5 兜底完全相同文本；
- 为什么选 SimHash：O(1) 指纹比对、对局部改写（换公司名/调语序）鲁棒，比逐字 diff 高效。重复 JD **排除出交叉验证**，避免"复制 N 份"虚增可信度。
- 实测：8/8 植入抄袭样本检出（另自动检出 3 条模板高度相似的近重复），0 误伤。

**② 能力通胀检测**
- 通胀特征：单条 JD 技能数远超同岗位中位数，且大量是"非共识/冷门"技能；
- 判据：`技能数 ≥ max(10, 中位数×1.4) 且 (技能数−中位数) ≥ 4` **且** `非共识技能占比 > 35%`（非共识=在簇内 <20% 的 JD 出现）；
- 以"非共识占比"为主判别量，避免误伤合理的高要求 JD。实测 17/17 检出。

**③ 时滞与质量**：按 `publish_date` 计算时滞，新鲜度 = 0.5^(天数/180)（半衰期 180 天）指数衰减，旧数据在聚合时降权。

### 3.2 反幻觉交叉验证（最核心创新）

**思想**：单一来源（含大模型臆造）不可信；只有**多源交叉验证**的能力才高置信进入图谱。

**置信度公式**（统一线性加权，全系统唯一，`services/confidence.py`）：
```
C = 0.35·支持率 + 0.20·来源多样性 + 0.15·时效性 + 0.20·来源权威度 + 0.10·外部验证
```
- **支持率** = 提及该技能的独立 JD 数 / 有效（非重复）JD 总数（主导项）；
- **来源多样性** = 独立雇主实体数/3 封顶（同一雇主经多个平台分发仍只计一个来源；封顶值冻结）；**时效性** = 新鲜度均值（半衰期 180 天）；
- **来源权威度** = 官网/政府平台 1.0、公开数据集 0.7、网络检索 0.6 的加权均值；**外部验证** = 联网检索或权威文件佐证 0/1；
- 五因子均 ∈[0,1]、权重和为 1 → C 天然 ∈[0,1]，**每一分可拆解**：前端点击置信度徽章即弹出五因子分解条（值×权重=贡献），新岗位发现路径与既有岗位路径共用同一公式，仅因子来源不同。

**三重防控**：
1. **必备门槛**：必备技能须由 ≥2 个独立雇主实体支持（同雇主跨平台去重），否则降级为加分（防单源臆造变"必备"）；
2. **置信度过滤**：confidence < 0.45 标为 candidate，不进入正式图谱；
3. **证据溯源**：每个能力项存多条 evidence（JD 片段/外链），前端可逐项追溯 → 可解释、可审计。

### 3.3 语义匹配 + 退化守卫（工程亮点）

- 匹配以**词典归一化精确匹配**为主，BGE 向量**语义匹配**为辅；
- **发现的问题**：bge-small-zh 是中文模型，对纯英文 token（Spark/Hive/Java）返回**退化向量**（不同词余弦≈1.0），会把"相关但不同"误判为"等价"，掩盖真实缺口；
- **守卫**：语义匹配仅在"双方均含中文字符"时启用，并加退化守卫（不同串余弦≥0.999 直接忽略）；
- **效果**：人岗匹配分类准确率 86.9% → **100%**。体现对模型局限的工程化防控。

### 3.4 多维匹配评分

```
综合匹配度 = 100 × (0.62·必备覆盖率 + 0.16·加分覆盖率 + 0.14·级别匹配 + 0.08·领域相关)
必备覆盖率 = Σ(命中权重 × 级别因子) / Σ权重     级别不足时×0.65
```

### 3.5 学习路径拓扑排序

- 对缺失的必备技能，依据 `skill_relation` 的 **prerequisite（先修）** 边计算深度；
- 按 (先修深度 升序, 重要度权重 降序) 排序，得到"先学先修、再学重点"的分步路径。

### 3.6 新岗位发现（RAG 接地）

- `关键词 → Tavily+Serper 双源检索证据 → 大模型基于证据生成定义（约束"不臆造、技能名简洁"）→ 对每个技能做证据校验 → 入库`；
- 不是让大模型"凭空想"，而是"有据可循"，从源头降幻觉；独立检索服务数纳入新兴度评估。

### 3.7 演化 diff 与可举证的淘汰判据（方法论亮点）

演化 diff 把新旧能力快照比对成 **新增 / 淘汰 / 修改** 三类变更。其中"淘汰"是最容易做错、也最容易被评委追问的一类，我们的做法有两个特点：

**① 我们主动查出并修掉了一个静默缺陷。** 上一轮结果是"删除 0 条"，本可以用"数据没给淘汰信号"解释过去；复盘时回读实现，发现**删除分支在原理上永远不可能触发**——调用方会把旧能力作为 `history` 先验注入新一轮聚合（为让历史证据参与打分，本身正确），旧能力名因而必然出现在 `new_caps` 中，`name not in new_caps` 恒为假，那是死代码。连带的更严重问题：旧能力若在新窗口支持不足被降级，**三个分支都进不去、变更日志一条不留地静默消失**，审计链在此断掉。

**② 判据先定、结果后看，且主动调严。** 修复后的淘汰判据四条同时成立：`window_skill_names`（先验注入**之前**的窗口原文技能名集合）中一次未出现 + 原为**必备能力** + 窗口 **JD 数 ≥20** + 支持减弱者改记 modify。第三条是被假阳性逼出来的——门槛 10 时，16 条 JD 的运维岗把 **Nginx** 判成淘汰；提到 20 后假阳性消失，代价是薄窗口岗位主动不下结论（**牺牲召回换取每条淘汰都可举证**）。修复后实测 **143 条淘汰 + 111 条修改**，Java 岗一次判出 23 项经典技术栈退场。详见 Q6-1。

## 四、技术选型理由

| 选型 | 理由 |
|------|------|
| **DeepSeek** | OpenAI 兼容、中文强、性价比高；JSON 强约束 + 低温度做可控抽取 |
| **BGE 向量** | 本地化中文向量服务，免费、低延迟；用于语义匹配/去重/RAG（并已对其英文退化做守卫）|
| **Tavily + Serper 双源** | **两个独立检索来源**本身就是交叉验证，单源易偏 |
| **MySQL** | 关系型天然适合"节点+关系+证据+版本"的图谱建模，运维成熟；规模可控时性能足够 |
| **FastAPI** | 异步、Pydantic 强类型、自动文档；服务层与框架解耦，便于单测（覆盖率 73%，146 用例）|
| **React+ECharts** | 力导向图/雷达/仪表盘等数据可视化生态成熟，交互流畅 |
| **systemd 单进程托管** | 服务器内存仅 1.6GB，单 uvicorn 同端口托管前端，常驻 ~80MB，`MemoryMax=420M` 防雪崩；亦提供 Dockerfile |

## 五、关键指标如何达成（可信度说明）

- **测试集是带真值标签的受控验证集**：379 条 JD + 18 份简历，每条都有 ground-truth，**含 8 抄袭 + 17 通胀对抗样本**，并非"挑容易的"；
- **生产图谱另有 3090 条真实语料**（5 类渠道 / 6 个 source、21 个采集批次）与之分轨：评测用受控夹具、上线用真实数据，两者互不污染；
- JD 解析 F1 98.25%：得益于"反幻觉提示工程 + 同义词归一化"，对真值技能高召回、对软技能不罚精确率；
- 简历提取召回 100%：大模型抽取 + 词典规则**兜底补漏**（缩写/同义词）；
- 匹配 100%：词典归一化精确匹配 + 退化守卫，避免语义误匹配；
- 全流程**一键复现**：`generate_dataset → run_pipeline → evaluate all → pytest`。

## 六、预期答辩问题与参考回答（Q&A）

**Q1：准确率这么高，是不是测试集自己造的、太简单？**
A：测试集是**带真值标签的受控验证集**，这是可量化评测的标准做法；且我们**故意植入了 8 条抄袭、17 条通胀对抗样本**来检验清洗鲁棒性，全部 100% 正确处理。指标脚本开源可一键复现。此外生产图谱走的是另一条轨道——3090 条真实采集 JD，在真实噪声下 SimHash 检出 230 条重复、通胀检测标记 460 条 JD，四道清洗工序（去重、通胀、时滞降权、同义词归一化）在真实数据上同样跑通。

**Q2：你们怎么防止大模型"幻觉"？**
A：三重防控——①**交叉验证门槛**：必备技能必须由 ≥2 个独立雇主实体支持（同雇主跨平台去重），否则降级；②**置信度过滤**：低于阈值的能力项不进图谱；③**证据溯源**：每项能力都挂可追溯证据。本质是"不信单一来源、只信多雇主共识"，并把可信度量化为 confidence。

**Q3：招聘数据有抄袭和通胀，你们怎么处理？**
A：抄袭用 **64 位 SimHash + 海明距离≤3** 近似去重，重复样本排除出交叉验证（否则复制 N 份会虚增可信度）；通胀用"技能数超中位数 + 非共识技能占比高"判别，通胀技能因缺乏交叉验证被自然过滤。实测 8/8、17/17 检出。

**Q4：嵌入模型是中文的，英文技能名怎么匹配？**
A：这正是我们发现并解决的一个真实工程问题——中文向量模型对纯英文 token 返回退化向量，会误判。我们的对策是：**英文同义词走词典归一化**（k8s→Kubernetes、torch→PyTorch），**语义匹配只用于中文技能并加退化守卫**。这个守卫把匹配准确率从 86.9% 提到了 100%，说明我们不是盲用大模型，而是了解并防控其局限。

**Q5：新岗位会不会是大模型编造的？**
A：不会。我们用 **Tavily + Serper 两个独立检索服务**先检索真实网络证据，大模型**基于证据**生成定义（提示词明确"禁止臆造证据没有的内容"），并对每个生成技能做证据校验、记录独立检索服务数与证据链接。是"有据可循"而非"凭空想象"。

**Q6：图谱怎么体现"动态演化"？**
A：两个维度。**时间维度**：我们有三个真实时间切片——2018-12（51job 公开数据集）、2024-07（HuggingFace 公开数据集）、2026-07（腾讯/网易/飞书 ATS/国聘四类主要分发渠道），按时间顺序依次灌入同一条演化服务链：解析 → 与历史能力交叉验证聚合 → **diff 出新增/淘汰/修改**，每条变更附更新说明、数据源（渠道+JD 数+批次）、置信度，岗位版本号自增；交叉验证仍按独立雇主实体归一化。结果是 **621 条真实变更记录（新增 367 / 淘汰 143 / 修改 111）**，版本分布 v1 17 岗 / v2 9 岗 / v3 6 岗（v1 中 14 岗是 2018 语料里完全检索不到的，另 3 岗为后续补齐物联网覆盖时新建、仅有 2026 一个切片）。**级别维度**：同一岗位按初/中/高分桶做画像 diff，得到晋升路径。淘汰的技能标记 deprecated 但保留历史，可回溯。
> 最有说服力的一个真实结果：**Java 开发工程师被判出 23 项必备能力淘汰**——Struts、J2EE、Hibernate、SpringMVC、Tomcat、Memcached、SQL Server、Dubbo、Oracle、MyBatis…… 一整套经典 SSH/SSM 老技术栈集体退场，同时新增大语言模型、RAG、云原生。这不是我们编的示例，是判据机械跑出来的。淘汰判据与其中一处我们自己修掉的缺陷见 Q6-1。

**Q6-1：你们的淘汰判据是什么？会不会误判？**
A：**会，而且我们踩过一次，正是踩过之后才把判据定成现在这样。**先说判据，四条同时成立才下淘汰结论：

| # | 判据 | 为什么必须有这一条 |
|---|---|---|
| ① | 判"消失"用的是 **`window_skill_names`——先验注入之前、最新窗口 JD 原文里真实出现过的技能名集合**，判据 = "该能力在最新 N 条 JD 中一次都没出现" | 聚合时旧能力会作为 `history` 先验被注入，**用聚合结果判淘汰在原理上判不出来**（详见下一段）。改用窗口原文后，每条淘汰都能回到具体 JD 举证 |
| ② | **只对「必备能力」的消失**下淘汰结论 | 加分项进出频繁、不同语料用词差异极大。实测把加分项计入，**一次就刷出 160+ 条假"淘汰"**——Java 岗 189 条里 166 条是加分项，真信号被彻底淹没 |
| ③ | **窗口 JD 数 ≥20** 才允许下淘汰结论 | 这是被假阳性逼出来的：门槛设 10 时，只有 **16 条 JD 的运维岗把 Nginx 判成了"淘汰"**。窗口太薄，一个天天在用的技能碰巧没被提到就能造出这种一眼被看穿的错误。提到 20 之后假阳性消失，运维（16 条）、大数据平台（13 条）这些薄窗口**主动放弃下结论**——缺证据不等于反证 |
| ④ | 仍出现在新 JD 里、但支持减弱被降为候选的，记 **modify**（"降级为候选能力项，保留观察，未淘汰"） | 不把"支持变弱"和"消失"混为一谈，同时保证这类事件不被静默丢弃 |

**这里有一个我们主动交代的缺陷修复，它比数字本身更能说明我们的方法**：上一轮跑完的结果是"删除 0 条"。我们本可以解释成"数据没给淘汰信号"，但复盘时回去读了 diff 实现，发现**删除分支在原理上永远不可能触发**——调用方会把旧能力当作 `history` 先验注入新一轮聚合（这本身是对的，为了让历史证据参与打分），于是旧能力名必然出现在 `new_caps` 里，`name not in new_caps` **恒为假**，那段代码是死代码。更严重的是：一个旧能力若在新窗口支持不足被降级，它**三个分支都进不去**，变更日志里**一条记录都不留、静默消失**——一个本该被审计的能力衰减事件就这样从链上蒸发了。我们补上第 ④ 条判据把它接住。

**关于误判，两点如实说明**：
1. **判据是"宁可少判、不可错判"**。第 ③ 条明确牺牲了召回——样本薄的岗位一条淘汰都不出，所以 143 条是**下限**不是全量。理由很直白：一条 Nginx 假阳性足以让整套演化结论的可信度归零，漏判的代价小得多。
2. **现存的已知噪声我们主动摆出来**：Java 岗 23 项淘汰里的 **Django、Flask 是 2018 语料的聚类污染**——这两个 Python Web 框架在建 2018 基线时被误归入 Java 岗位簇，它们的"淘汰"是历史聚类噪声被新语料修正，**不是真实技术退场**。我们没有把它从清单里悄悄删掉，因为判据是机械执行的、没有为了结果好看做人工挑选；这条噪声也正好指向下一步该改进的岗位聚类精度。

**一句话总结**：我们不是把参数调到"能跑出删除"为止，而是**先定可举证的判据、再看结果**，中途还主动把假阳性门槛从 10 提到 20、牺牲了一部分召回。

**Q7：和传统关键词匹配有什么本质区别？**
A：传统是静态、字符级、不可信；我们是**动态感知 + 语义/级别多维 + 可溯源置信度**。能回答"技术 A 爆发会给岗位 B 带来哪些新技能"——通过技能-技能的 drives（驱动）关系与岗位能力的动态演化来表达。

**Q8：数据规模偏小，真实场景能用吗？**
A：目前生产语料是 **3090 条真实 JD、5 类渠道 / 6 个 source、21 个采集批次**，已不是"演示级"。更重要的是架构与岗位、规模无关：pipeline 支持任意量级 JD（解析已做并发），交叉验证在数据越多时统计越显著、过滤越精准。接更多合规数据源即可继续扩展，方案可平滑迁移到医疗/金融/制造等领域。

**Q9：MySQL 存图谱，为什么不用 Neo4j？**
A：我们的图谱是"岗位-技能-证据-版本"的有界关系，MySQL 关系建模 + 应用层组装图 JSON 已满足查询与可视化需求，运维成熟、与现有 MySQL 复用；技能-技能关系也已建模（先修/相关/驱动）。规模进一步增大时可平滑迁移图数据库。

**Q10：覆盖率 73%，没覆盖的是什么？**
A：146 个用例全部通过，核心业务逻辑（清洗、反幻觉聚合、置信度公式、同义词归一化、匹配、抽取后处理、人才侧图层）都是高覆盖，另有 27 个用例专门锁两条写库路径的破坏性防护（重建不得冲掉已演化岗位、演化不得静默降级、发现接口不得覆盖既有岗位）、7 个用例锁演示站只读闸门（只读时写路径 403 或降级为 dry-run 且库表零变动）、27 个用例锁人才侧的脱敏落库与别名学习四道护栏；未覆盖的主要是外部调用封装（LLM/检索，依赖网络）与一次性编排脚本，这部分用集成/冒烟测试与线上验证覆盖。

**Q11：涉及招聘数据与简历，怎么保证数据合规与隐私？**
A：我们把合规作为图谱科学性的支柱之一，覆盖数据全生命周期：①**来源合规**——只采集公开 JD 与公开网络证据，39 个候选源逐一实测 robots 与入口，**全部聚合类招聘平台（BOSS直聘/智联/猎聘/拉勾/牛客/前程无忧/实习僧）一条数据都未采**，不复现反爬签名、不解密自定义字体、不过人机校验、不碰登录墙，数据最小化；②**PII 最小化**——简历仅在内存解析用于本次匹配，**原始简历与姓名等个人信息一律不落库**，服务端仅留存脱敏技能要素（`resume.redact_for_storage` + `match.py`），前端明示隐私声明；采集侧同样有 PII 字段护栏（字段名含 phone/email/联系人 直接抛错）与正文正则打码；③**可溯源可审计**——每个能力项保留证据链，可逐项追溯；④**人工监督**——模型产出是辅助建议、非最终决策，岗位与能力项均可人工增删改并记录变更；⑤**公平性**——只用技能要素匹配，不采集性别/年龄/院校等敏感特征，多源交叉验证削弱单源偏见。合规与反幻觉同源：交叉验证既反幻觉也反偏见，证据溯源既可解释也可审计。

**Q12：数据是哪来的？是不是大模型生成的？**
A：不是。生产图谱语料全部来自合法采集或公开许可的真实招聘数据，共 **3090 条、5 类渠道 / 6 个 source、21 个采集批次**：

| 平台批次 | 条数 | tier | 权威度 | 说明 |
|---|---|---|---|---|
| 飞书招聘 SaaS 企业官网 | 1022 | official | 1.0 | 11 家企业官方招聘官网；初始 r2 入库 629 条，物联网专项补入 145 条，2026R6T2 / 2026R6T3 / 2026R7H 批次扩采 |
| 国聘网 | 943 | gov | 1.0 | 中央广播电视总台主办的国家级公共招聘平台；初始 r2 入库 571 条，物联网专项补入 68 条，数字孪生/数字人专项补入 32 条，2026R6T2 / 2026R6T3 / 2026R7H 批次扩采 |
| 51job2018 公开数据集 | 300 | dataset | 0.7 | 2018-12 历史基线（GitHub 公开仓库） |
| AI_Job 2024 公开数据集 | 300 | dataset | 0.7 | 2024-07 中间基线（HuggingFace，AFL-3.0 许可证） |
| 腾讯招聘 | 272 | official | 1.0 | 官网公开接口，r1/r3/r5 累计 |
| 网易招聘 | 253 | official | 1.0 | 官网公开接口，r1/r3/r5 累计 |

采集全程无需登录、robots 逐 host 检查、单站 ≥4 秒控频、不采任何个人信息（字段名拦截 + 正文打码）；每条 JD 有本地 jsonl 原始留存 + manifest + 每请求一行的 crawl_log，数据库记录平台/公司/原始 URL/发布时间/采集批次，首页"数据源台账"可直接查看。大模型只做**抽取**（把 JD 文本解析成结构化技能），不生成任何语料。早期的模板合成数据集被重新定位为"对抗测试夹具"——专门注入抄袭/通胀样本验证清洗算法检出率，不进图谱。

**Q12-1：飞书那批数据合规吗？是不是绕过了人家的反爬？**
A：没有绕过，这一点我们写得很明确。三条：①**全程未登录**，不注册账号、不带任何 Cookie 身份；②接口需要的 csrf token 由 `/api/v1/csrf/token` **面向所有访客公开下发**（包括未登录访客），是会话卫生机制而不是访问控制，取用它不构成"绕过权限"；③浏览器请求上确实带一个 `_signature` 反爬签名，我们**既没有逆向也没有复现它**——实测把这个参数整个去掉，接口照常返回 200 和同样的公开职位数据，这恰恰说明接口本身对公众开放，我们只是用更朴素的方式访问了同一份公开数据。另外这些站点是**企业自己的官方招聘官网**（托管在飞书招聘 SaaS 上，域名 `{企业}.jobs.feishu.cn`），性质与腾讯/网易招聘官网一致，所以定 tier=official、权威度 1.0。租户也不是随便挑的：探测了 95 个候选 slug，只采公开职位数 > 0 的 11 家。依据在 `data/collect/采集合规说明.md` 与 `probe_ats_report.json`。

**Q12-2：为什么不采 BOSS直聘、51job 这些主流招聘平台？数据量不是更大吗？**
A：**因为实测下来它们要么 robots 明确禁止、要么必须破解反爬，我们一条都不采**。这不是没查，恰恰是查过才不采——本轮用 `probe_sources.py` 对 **39 个候选站点**逐一取 robots.txt 并对入口发 1 次 GET（探测阶段不采任何数据），逐条结论是：

| 平台 | 实测结论 | 处置 |
|---|---|---|
| BOSS直聘 | robots.txt 明确 Disallow `/*?query=*`、`*?city=*`、`*?position=*`、`*?salary=*`、`*?experience=*` —— **正是职位检索必需的查询路径** | 不采 |
| 猎聘 | robots.txt `Disallow: /*?*`，禁止一切带查询串的 URL | 不采 |
| 前程无忧 51job | 站点无 robots.txt，但搜索接口有**阿里云 WAF 人机校验** | 不采（不破解反爬） |
| 智联招聘 | robots 未禁 `/sou/`，但检索接口需要**页面 JS 生成的反爬令牌** | 不采（不复现反爬签名） |
| 拉勾 / 牛客 | 入口与 /robots.txt 返回**同一个等长（11027 字节）WAF 拦截页**，含 login/captcha 特征 | 不采 |
| 实习僧 | robots 不禁止任何路径，但岗位标题与数字**用自定义字体加密**，取明文必须解码字体映射＝绕过技术保护措施 | 主动放弃 |
| 京东 / 美团 | 入口 302 跳登录页 / 接口要求登录 | 不采（不碰登录墙） |

同样的标准也用在数据集上：阿里天池（需登录+学生认证）、和鲸 Heywhale（需注册登录）、textdata.cn（需加微信索取）**一律未下载**，最终选用 HuggingFace 上许可证明示（AFL-3.0）、直链可下、无需登录的公开数据集。

这里有一个必须主动交代的口径问题：我们的探测脚本判定"robots 是否禁止目标路径"时**只比对 URL 路径、不含查询串**，所以 BOSS直聘、猎聘这类"用查询串规则禁止检索"的站点，脚本机械判定是"否"；但**实际的职位检索必然携带查询串、必然命中其 Disallow 规则**，所以我们在报告里按真实语义判定为"不采"，而不是拿脚本的机械结论给自己开绿灯。这一点写在 `数据源实测报告.md` 的"读表须知"里。

**结论一句话**：39 个候选源逐一实测后，我们只对**企业官方招聘官网**与**国家级公共就业平台**两类无登录墙、无反爬、robots 未禁的公开接口采集数据；**所有聚合类招聘平台一条都没有采**。少拿到的数据量，我们用"多个企业官网 + 国家级平台 + 公开历史数据集"的组合补上了——这也是我们敢说数据"可信、可查、可问责"的底气。

**Q13：新兴岗位凭什么说它"新兴"？**
A：双判据+权威佐证。判据：①近两年（2025/2026 最佳）新出现，或 ②曾出现→沉寂→复兴。佐证分级：人社部新职业/新工种文件（如 2026-07-02 公示的"智能体开发员"工种、"具身智能机器人应用技术员"新职业；2025-07-22 第七批的"生成式人工智能系统测试员"）> 头部机构报告（翰德/脉脉/麦肯锡）> 多源网络证据，文件原文快照本地归档、逐岗位挂载可查。当前生产库共有 **21 条 AuthorityEvidence，覆盖 19/32 个岗位；6/6 新兴岗位全部覆盖，其中新兴岗位挂 8 条**。补齐时对 26 个缺口逐一考证，只录入 13 条能由一手文件逐字核验的材料；另 13 个找不到或对应关系牵强的岗位不硬凑。复兴型案例：人工智能数字人训练师（元宇宙期火→退潮→2024-08 人社部增设工种+大模型驱动复兴）。系统还能反向识别"回落"：提示词工程师已按报告证据降级为常规岗位并记录演化叙事。

**Q14：当前置信度怎么算？为什么与历史口径不同？**
A：唯一公式 C = 0.35·支持率 + 0.20·来源多样性 + 0.15·时效性 + 0.20·来源权威度 + 0.10·外部验证，五因子全部落库，前端点击任何置信度徽章都能看到五因子分解（每项的值、权重、贡献分）。**假设算例**：某技能被 9/13 条有效 JD 提及（0.69）、覆盖 3 个独立雇主实体（归一化去重后 3/3=1.0 达封顶）、新鲜度 0.88、全部官网/政府来源（1.0）、无外部验证（0）→ C≈0.78。岗位整体置信度是粗粒度 active 能力项的权重加权平均。

当前 R6 最终生产均值为 **0.5502**（2026-08-30 口径）；26 个既有岗位均值 **0.5271**，6 个新兴岗位均值 **0.6507**（同一口径日期）。

置信度**带日期是必需的，不是谨慎**：五因子里的「时效性」随 JD 变旧而下降，服务器上的置信度批算调度器每天 02:30 按当天 `as_of` 重算一次（它属于系统自有重算，不在 `READ_ONLY` 闸内），因此全库均值会以约 **-0.0003/天** 的速度自然衰减：实测 +1 天 0.5499、+7 天 0.5481、+30 天 0.5417、+90 天 0.5275。**这是设计特性而非缺陷**——语料不更新则置信度自然回落，正是「动态演化」在分数上的体现；要维持高置信度就必须持续补充新语料。所以本材料里的均值一律标注口径日期，评委在不同日期打开线上站点看到的数会略低于此处，属预期行为。同时实测了 +1/+7/+30/+90 四个时点，「active 但独立雇主 < 2」的违规数**始终为 0**——闸门不会因时间流逝被重新突破，夜间批算还会持续强制这条闸门（只降级、绝不自动升级，见 `confidence_batch._job_calculation`）。这是「一次修复 + 持续守护」的完整证据链。R6 整改前只读基线为 **0.4783**；更早材料采用过不同数据状态下的均值，均不作为当前值。

R6 完成了 13 条严格考证的一手权威佐证补齐、雇主实体归一化、细粒度能力补闸和统一五因子重算；同时摘除 155 个错挂 JD—岗位对、删除 605 条错误 Evidence、将 64 条失去交叉验证支持的 active 降为 candidate。收尾时又在影子库上把「≥2 个独立雇主才能 active」这道闸门对全库补跑了一遍，查出 **48 条 active 实际只有 0 或 1 个独立雇主支撑**——历史遗留，非本轮引入——全部降为 candidate，active 860→**812**、candidate 3556→**3604**，证据链保留、**无任何 candidate 被自动升级**。**均值 0.5356→0.5502 的上升是这一步的副作用，不是我们把分数调高了**：被降级的正是置信度最低的一批（多在 0.16–0.33），移出 active 后剩下的平均值自然上升。这个数字如果被当成"改进成果"来讲，就是不诚实的。这 48 条的根因是可以指名道姓的：它们的证据 JD 绝大多数来自公开数据集 `dataset_aijob2024`（`huggingface.co/datasets/RocXuLi/AI_Job_DataSet_1000_`），而这批语料是**匿名化的——`company` 字段本身就是空的**。所以问题不是"证据不够多"，而是**这类来源在原理上就无法证明独立雇主**，理应过不了「≥2 个独立雇主实体」这道闸门。闸门把"匿名语料堆出来的能力项"挡在 active 之外，正是它被设计出来要做的事。受影响的只有 8 个岗位（自动驾驶算法工程师 8→2、机器人算法工程师 10→4、多模态算法工程师 17→11、AIGC算法工程师 16→13，大模型算法工程师 / 大模型推理优化工程师 / 智能硬件开发工程师 / 生成式人工智能系统测试员 各降 2–3），**其余 24 个岗位的 active 数完全没变**。人工智能数字人训练师修复后只剩 1 个契约能力簇，按证据不足展示，不用错证据补齐页面。

**公式、五因子权重、多样性封顶值（3）、过滤阈值（0.45）均未逐岗调整。** 当前来源多样性按独立雇主实体去重，分数变化由关系状态、雇主级支持、权威佐证、时效与外部验证共同决定，不能沿用"多平台使均值上升"的旧解释。有效非重复 JD 中雇主已识别 **2561/2860（89.55%）**；RoleContract 已评估 32 岗，**6 岗 ready（18.75%）**。ready 是满足 8–12 个同粒度能力簇门槛的治理投影，不是岗位存在性的判断。

**Q15：中级和高级工程师的能力差异怎么体现？**
A：真实 JD 采集时按标题（高级/资深）与经验年限（0-3/3-5/5+ 年）推断级别分桶，各桶独立跑同一套交叉验证聚合得到分级画像，"中级→高级"就是两桶画像的 diff：晋升需新增掌握哪些技能、哪些技能权重/掌握深度要求提升、哪些初级要求在高级 JD 中不再单列（默认前提）。R6 最终 `job_level_skill` 共 **828 条，覆盖 27/32 岗**，越界 **0/828（0.0%）**。没有画像的是 **5 个岗位**（机器人算法工程师、自动驾驶算法工程师、人工智能数字人训练师、提示词工程师、智能硬件开发工程师）；它们当前证据不足，因此清空历史画像，不用失效残影撑页面。其中两个是本轮补闸降级后才退出的：画像必须与岗位 active 能力集取交集，能力项被降为候选后，该岗位就凑不满 2 档。修复的根因是画像生命周期：旧实现只删除当前精确切片，已失效的 `track/industry/recruitment` 切片和被跳过岗位的旧行会残留；现改为整岗位目标状态替换，不达标也清旧画像。演化页"级别演化"模式对有画像的 27 岗展示初→中→高阶梯视图。

**Q16：2018→2024→2026 的演化里，新增能力那么多，是真的能力增长还是数据变多了？**
A：**必须承认，两者都有，而且我们没法完全分开。** 三个时间切片的来源丰富度并不对等：2018 与 2024 两个切片**各自只有单一公开数据集渠道**，交叉验证机制在这两个切片上天然拿不到多雇主支持，所以它们确认下来的能力项偏少；2026 切片覆盖腾讯、网易、飞书 ATS、国聘四类主要分发渠道，但交叉验证仍按独立雇主实体去重，同雇主跨平台不重复计数。结果就是 621 条变更里有 493 条落在 2026 这一步，**其中一部分来自来源丰富度提升，而不是纯粹的岗位能力增长**。同样地，淘汰结论也受语料用词偏好影响（Java 岗 23 项淘汰里的 Django/Flask 就是 2018 语料聚类污染被修正，见 Q6-1）。我们在测试报告里专门写了这条局限，不把它包装成"八年间能力爆发式增长"。要消除这个效应，得补齐历史年份的多源语料（更多年份的公开数据集、政府平台历史归档），让各切片的来源结构可比——这是我们列出的后续工作。

不过有一类证据不受这个问题影响：**14 个岗位在 2018 语料里完全检索不到**（大模型算法、AI 智能体开发、具身智能、数字孪生、AIGC、多模态、自动驾驶、数字人等）。这不是"提及次数少"，是"根本不存在"，无论来源多少都不会改变结论——这是"新岗位涌现"最硬的直接证据。

## 七、技术难点与解决

| 难点 | 解决 |

## 八、局限性与改进方向（体现深度与诚实）

- **时间切片来源不对等（最需要如实说明的一条）**：2018 与 2024 两个切片各自只有单一公开数据集渠道，交叉验证拿不到多雇主支持，确认的能力项偏少；2026 切片覆盖四类主要分发渠道，但交叉验证按独立雇主实体归一化，同雇主跨平台不重复计数。因此演化变更绝大多数落在 2026 一步（493 / 621 条），**其中一部分来自来源丰富度提升而非纯粹的岗位能力增长**。→ 后续补齐历史年份的多源语料（更多年份公开数据集、政府平台历史归档），使各切片来源结构可比。
- **淘汰判据牺牲了召回，且残留聚类噪声**：按"窗口 JD 数 ≥20"的门槛，样本薄的岗位（运维 16 条、大数据平台 13 条）主动不下淘汰结论，143 条淘汰是**下限**；已判出的淘汰里，Java 岗的 Django/Flask 属 2018 语料**聚类污染**被新语料修正，非真实技术退场（见 Q6-1）。→ 提升岗位聚类精度、补齐薄窗口语料。
- 2024 数据集只有「岗位名 + 技能标签 + JD 正文」，无 company/location/salary 字段（留空而非臆造），且样本集中在 AI/算法方向，因此 Java/后端/数据分析等传统岗位簇仍只有 2018 与 2026 两个观测点；
- **匿名语料撑不起交叉验证（本轮补闸暴露的一条）**：48 条被降级的 active，证据几乎全部来自 `dataset_aijob2024` 这个 `company` 字段为空的匿名公开数据集，在原理上无法证明独立雇主，因而过不了「≥2 个独立雇主实体」闸门；受影响的 8 个岗位以自动驾驶、机器人算法为主。→ **针对这 8 个岗位定向补采带雇主署名的真实 JD，这批能力项就能凭真实交叉验证重新回到 active**。这是有明确路径的改进项，不是遗留缺陷；本轮不做，是因为补采会再次改动全部头条数字，而发布口径必须先冻结。
- 当前向量模型对英文较弱 → 可接入更强的双语/领域向量模型增强语义匹配；
- 技能先修关系部分依赖人工先验 → 可从大规模简历/课程数据中学习先修依赖；
- 趋势预测尚为静态 → 可引入时间序列对技能热度做趋势外推（技术 A 爆发的前瞻预警）；
- 数据源可继续扩展更多合规信源（中国公共招聘网的公开查询接口本轮返回 502，已列为后续扩展源），进一步提升统计显著性。
