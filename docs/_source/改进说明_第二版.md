## 一、本轮（第二轮）重点：意见 ⑤ 与 ⑦

这两条是上一轮改过、但老师复看后指出仍有问题的。本轮把它们查到根上。

### 意见⑤ —— 为什么那 6 个新兴岗位只有几个"大概念"

老师看到的现象是真的：具身智能工程师点进去只有 Python / C++ / 大语言模型 / ROS / PyTorch 五项，
而同一个系统里 AI 产品经理有 14 项粗粒度能力、每项下面还挂十几个细分技能点。
**同一个系统里两个岗位的颗粒度差了一个数量级**，这不正常。

查下去发现，原因不是数据不够，而是**这 6 个岗位走的根本不是同一条建图路径**：

1. 它们由「联网检索证据 + 一次大模型定义」生成，**完全不读 JD 语料**；
2. 这条路径的输出格式里**没有"父技能"这个字段**，而系统正是靠这个字段建立两级技能树——
   没有它，生成的能力项在结构上**永远只能是粗粒度**，跟提示词写得好不好无关；
3. 更麻烦的是，这个脚本落库时是"先清空再重建"，即使先用真实语料建好过，再跑一次就被覆盖掉。

**改法**：这 6 个岗位的真实 JD 其实早就采集入库了（智能体 112 条、推理优化 89 条、
具身智能 39 条、数字孪生 23 条、生成式测试员 18 条、数字人 14 条，共 295 条），
只是没被用上。本轮把它们改由主链路重建。结果：

| 岗位 | 粗粒度必备能力 | 已交叉验证的技能点 | 候选技能点 |
|---|---|---|---|
| AI智能体开发工程师 | 5 → **37** | 0 → **87** | 512 |
| 大模型推理优化工程师 | 5 → **33** | 4 → **65** | 499 |
| 具身智能工程师 | 5 → **18** | 0 → **23** | 220 |
| 生成式人工智能系统测试员 | 3 → **15** | 2 | 84 |
| 数字孪生工程技术人员 | 3 → 5 | 2 | 48 |
| 人工智能数字人训练师 | 4 → 4 | 2 | 38 |

具身智能工程师现在是 18 项粗粒度能力，其中「具身智能」下面挂着
模仿学习 / VLA视觉语言动作模型 / MuJoCo仿真 / 机械臂操作，
「ROS」下面挂着 ROS2开发 / Gazebo仿真 / DDS / Cyber RT——
这些词全部来自真实招聘 JD 原文，且都通过了「≥2 个独立来源交叉验证」这道闸。

**两点必须如实说明**：

- **数字孪生工程技术人员（5 项）和人工智能数字人训练师（4 项）仍然偏薄。**
  我们为它们单独做了一轮定向采集，把检索词从「数字孪生」「数字人」扩到
  仿真建模 / 三维建模 / BIM / 语音合成 / 动作捕捉，采了 194 条、入库 47 条。
  **逐条核对后发现扩错了**：数字孪生新增的 31 条里标题命中 0 条，实际召回的是
  BIM 土建工程师、机械设计（CAE 仿真方向）、碳化硅功率芯片这些传统机械电力岗；
  数字人那批多数是「语音大模型算法研究员」——语音合成是数字人的组件技术，
  但和人社部定义的「数字人训练师」（数据标注、语料整理、交互训练）不是一个岗位。
  最后只保留了 1 条真正对口的，其余 46 条摘出了这两个岗位簇。
  这两个岗位是 2026-07 和 2024-08 才公示的新职业，市场 JD 供给本身就少。
  **我们宁可承认样本薄，也不靠放宽检索词把邻近岗位混进来凑数**——那只会让能力画像失真。
- **这 6 个岗位的置信度是下降的**，从 0.77–1.00 降到 0.53–0.59，其中数字孪生原来是 **1.000**。
  原因是上一版它们的置信度由「联网检索命中数」打分，本轮改与其他岗位走同一条 JD 交叉验证链。
  公式、五因子权重、阈值本轮一个都没改（26 个既有岗位均值 0.5483 全程未动，正是旁证）。
  **一个岗位在能力图谱里拿到 1.000 的置信度，本身就是应该被怀疑的信号；
  我们宁可要一个可解释的 0.55，也不要一个不可解释的 1.00。**

### 意见⑦ —— 演化历史与溯源证据

排查结论是：**功能都在，坏在三处"数据是对的、页面没说清楚"**。

| 老师看到的 | 实际原因 | 改法 |
|---|---|---|
| 溯源证据只有一排「87 来源 · 置信 92%」 | 证据卡片（公司 / 岗位名 / 发布日期 / 可点原始链接）代码是完整的，但整块包在默认折叠的容器里，而折叠的三角箭头又被样式去掉了——**页面上没有任何"这里能展开"的提示** | 补上展开箭头，前 3 条默认展开 |
| 展开后只有 6 张卡，和"87"对不上 | 87 是"提及该技能的 JD 数"，6 是"留存的代表性证据条数"。两个数字都是真的，**错在把它们混成一个词** | 文案改成「87 条 JD 提及 · 留存证据 12 条」，留存上限从 6 提到 12 |
| 新兴岗位点进去演化历史一片空白 | 岗位库按"新兴"排序，6 个新兴岗位排最前，**老师点开的第一个岗位必然是空的**。而它们本来就不该有跨时间切片的演化记录——2018 和 2024 的历史语料里检索到 0 条 | 改成说明视图 + 岗位溯源时间线（人社部公示日 → 首次可考证出现 → 市场 JD 首次采集到 → 当前 JD 数），并直接写出"本岗位在 2018 年（0 条）与 2024 年（0 条）历史语料中共检索到 0 条 JD" |

第三条我们做过一个取舍，想请老师评判：技术上完全可以让这 6 个岗位"有"演化历史——
保留权威文件定义的 v1，再用 2026 年真实 JD 跑一轮得到 v2，差异就是「政策定义 vs 市场实际」。
**我们模拟跑过，然后否决了**：这样会写出事实错误的淘汰记录——
「分布式推理」会被判定从大模型推理优化工程师岗位"需求消退"，
「仿真计算」「可视化开发」会被判定从数字孪生岗位退场。
这些词本来就是大模型从检索摘要里造出来的、从未在市场数据中出现过，
把它们标成"退场"等于断言一段不存在的市场轨迹。
**对一个以反幻觉为卖点的系统，审计日志里的假记录比页面上少几项能力严重得多。**
所以改成把"历史语料里检索不到"这个真实事实讲出来——它本身就是"新岗位涌现"最硬的证据。

**另外顺手修了一处老师没提、但更要命的自相矛盾**：Java 开发工程师的 23 项已淘汰能力
（Struts、Hibernate、SpringMVC、Memcached…）此前以正常颜色的「细分技能点」标签
渲染在能力画像上，和现行技能长得一模一样。老师在「演化历史」里看到「🔴 淘汰 Hibernate」，
退回「能力画像」又看到 Hibernate 挂在 Spring 下面——两个页面互相打脸，
而演化叙事恰恰是本作品的核心论据。现在改成独立的「已淘汰 N 项」折叠区 + 删除线。

## 二、前一轮已完成的整改（意见 ①②③④⑥）

**① 闭环**：全流程做成 采集 → 清洗 → 大模型抽取 → 反幻觉交叉验证 → 图谱与演化 → 人岗匹配 → 人工反馈回流。
首页可见真实漏斗：**采集 2570 → 查重后 2404 → 交叉验证确认 1158 / 单来源降级候选 3258 → 沉淀为 32 个岗位、3952 项技能**。
应用层的人工优化会写回演化记录，闭环两端真正接上。

**② 数据源**：第一版用的是模板合成的假 JD（假公司名 + example.com），本轮**全部退出生产图谱**，
只保留为对抗测试夹具（专门注入抄袭、能力通胀样本来验证清洗算法）。
生产图谱改由 **2570 条真实 JD** 构建，来自 6 个平台：飞书招聘 SaaS 企业官网 774、国聘网 671、
2018 年公开数据集 300、2024 年公开数据集 300、腾讯招聘 272、网易招聘 253。
采集全程有护栏（逐站检查 robots.txt、单站 ≥4 秒控频、不带任何登录态、不采个人信息），
原始留存 + 采集台账逐条可查。**39 个候选数据源逐一实测后，所有聚合类招聘平台
（BOSS直聘/智联/猎聘/拉勾/牛客/前程无忧/实习僧）一条数据都没采**——
原因分别是 robots 明确禁止、需过人机校验、需复现反爬签名、字体加密等，
我们选择不碰，逐条实测记录在《数据源实测报告》里。

**③ 新兴岗位判据**：形式化为两类——**新出现型**（近两年首次规模化出现）与
**复兴型**（曾出现→沉寂→重新兴起，如人工智能数字人训练师）。
6 个岗位每个都有权威佐证并归档原文快照：人社部 2026-07-02 公示（智能体开发员、
具身智能机器人应用技术员、数字孪生工程技术人员）、2025-07-22 第七批新职业
（生成式人工智能系统测试员）、2024-08 增设工种（人工智能数字人训练师），
以及脉脉、翰德等机构报告。反过来，曾经很火的「提示词工程师」被系统降级为常规岗位
并记录演化叙事——系统对岗位的"兴起 / 回落 / 复兴"具备双向识别能力。

**④ 置信度**：统一为一条线性加权公式，全系统只有一处实现：

> C = 0.35×支持率 + 0.20×来源多样性 + 0.15×时效性 + 0.20×来源权威度 + 0.10×外部验证

五个因子逐项落库，**前端点任意置信度徽章即可看到这一项是怎么算出来的**。
全库均值当前 **0.5613**。

**⑥ 级别演化**：真实 JD 入库时按标题（高级/资深/初级）与经验年限推断级别，
分桶后各自跑同一套交叉验证，得到初/中/高三档画像；"中级→高级怎么演化"就是两档画像的差异计算，
输出"晋升需新增掌握 X""Y 的权重要求从 45% 提到 72%"这类结论。
当前 **32 个岗位全部建有三档画像，共 1076 条分级能力记录**（上一版 29 个 / 916 条）。
这里也修过一个硬伤：分级画像原先是按级别桶独立重跑聚合，导致画像里出现岗位能力集里根本没有的技能，
**越界率 45.5%**（岗位页显示 7 项能力、级别页却列出 88 项）；改为与岗位能力集取交集后，
**越界率 0.0%**。

## 三、意见⑧ 团队成员简历读取学习（本轮未实现）

如实说明：**这一条本轮没有做。** 现状是简历功能只支持单份上传、即时匹配、
解析结果脱敏后落库但从不回读，没有任何"团队"概念。

要做成"读取学习团队成员简历"，需要新增：团队/成员的数据表、批量上传接口、
团队技能覆盖视图，以及"团队对某个目标岗位的能力缺口（谁能补、还缺谁）"的计算。
这会把系统的落脚点从"个人求职"扩展到"团队盘点"，与赛题的人岗匹配主线是一致的，
但属于一个新模块而非现有功能的修补。我们的判断是：在答辩前有限的时间里，
把①-⑦做扎实、每个数字都站得住，比多铺一个模块更重要。若老师认为这一条必须补上，
我们可以优先安排。

> **后续（第三轮）**：这一条已经补上了。上面列的四项（团队/成员数据表、上传接口、
> 团队技能覆盖视图、"谁能补/还缺谁"的缺口计算）全部落地，另外多做了一层
> **从简历语料学习技能表述**——这才是意见里"学习"二字的落点。
> 语料来源、四道护栏、留出集评测结果，以及**这个模块的边界与不足**，
> 见《改进说明_第三版》。本节文字保留为第二轮当时的如实记录，不作追改。

## 五、两轮整改里我们自己揪出来的三个缺陷

这几个老师没有提，但我们认为比页面观感更值得汇报，因为它们动摇的是"可信"这个根本卖点：

1. **演化的"删除"分支是死代码**。三个时间切片跑完结果是"删除 0 条"，看起来用
   "数据没给淘汰信号"就能解释过去。复盘时我们没接受这个解释，回去读了实现——
   旧能力会作为历史先验被注入聚合结果，所以判据 `name not in new_caps` 恒为假，
   **这个分支在原理上永远不可能触发**。修复后重新定了四条可举证的判据
   （淘汰必须是"在最新 N 条 JD 原文里一次都没出现"、只判必备能力、窗口 JD 数 ≥20、
   支持减弱的记为"降级候选"而非静默丢弃），跑出 143 条淘汰 + 111 条修改。

2. **变更日志与数据库事实背离**。线上演示站被点击后，我们发现某岗位 102 行能力被降级，
   而变更日志里一条淘汰记录都没有——两套逻辑各算各的。对一个卖"可溯源"的系统，
   **审计链本身不可信比丢几行数据严重得多**。现已改为由同一个判定结果驱动，
   并写了回归测试锁死。

3. **两条写库路径会用弱证据覆盖强证据**。"发现新岗位"接口对已存在的岗位调用建图函数，
   而该函数是"先清空再重建"，等于用十来项大模型现生成的能力物理删除 301 项交叉验证结果。
   现已改为拒绝覆盖并给出冲突提示，本轮又补了一层护栏：
   跑过演化的岗位默认拒绝重建，需要显式加参数。

**这三条都配了回归测试**（`test_rebuild_guards.py` 15 个 + `test_evolution_guards.py` 8 个），
不是修完就算，而是让它们不可能再次悄悄发生。
