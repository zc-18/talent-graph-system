### 3.1 JD 解析准确率

- **方法**：对 371 条非重复 JD 调用大模型解析，抽取必备/加分技能并归一化，与真值标签比对。
- **指标**：精确率 P、召回率 R、F1、重要度分类正确率。
- **结果**（`data/eval_jd_result.json`，n=371）：

```

召回率 Recall    : 0.9795
F1               : 0.9824
重要度分类正确率  : 0.9771
```

- **方法**：对 18 份简历解析抽取技能，与真值比对（软技能不计精确率惩罚）。
- **结果**（`eval_resume_result.json`）：

```
精确率 Precision : 0.937
召回率 Recall    : 1.000
```

### 3.6.1 淘汰（delete）判据与一次真实缺陷修复

**上一轮的结果是"删除 0 条"，我们没有接受"数据没给淘汰信号"这个解释，而是回去读了 diff 实现，结果发现删除分支在原理上永远不可能触发。**

- **缺陷**：调用方在做新一轮交叉验证聚合时，会把旧能力作为 `history` 先验来源注入（本身是对的，为了让历史证据参与打分）。于是旧能力名必然出现在聚合结果 `new_caps` 里，判据 `name not in new_caps` **恒为假**——删除分支是死代码。
- **更严重的连带问题**：若某旧能力在新窗口支持不足被降级为候选，它**三个分支都进不去**（不是新增、判不出删除、也不满足重要度/权重显著变化阈值），于是**变更日志里一条记录都不留、静默消失**——一个本该被审计的能力衰减事件从链上蒸发。

**修复后的四条判据**（`app/services/evolution.py::compute_changes`，先定判据再看结果，非事后调参）：

| # | 判据 | 定这条的实测依据 |
|---|---|---|
| ① | 传入 `window_skill_names`（**先验注入之前**、最新窗口 JD 里真实出现过的技能名集合）；淘汰判据 = "该能力在最新 N 条 JD 中**一次都没出现**" | 用聚合结果判淘汰在原理上判不出来；改用窗口原文后每条淘汰都可回溯到具体 JD 举证 |
| ② | **只对「必备能力」的消失**下淘汰结论 | 加分项进出频繁、不同语料用词差异极大。实测计入加分项会一次刷出 **160+ 条假"淘汰"**（Java 岗 189 条里 166 条是加分项），真信号被淹没 |
| ③ | **窗口 JD 数 ≥20** 才允许下淘汰结论（`MIN_JDS_FOR_DELETE = 20`） | 门槛设 10 时实测出现假阳性：只有 **16 条 JD 的运维岗把 Nginx 判成了"淘汰"**。提到 20 后该假阳性消失，样本薄的窗口（运维 16 条、大数据平台 13 条）**主动不下结论**——缺证据不等于反证 |
| ④ | 仍出现在新 JD 里但支持减弱、被降为候选的能力记为 **modify**（"降级为候选能力项，保留观察，未淘汰"） | 补上静默丢弃的漏洞，保证任何能力状态变化都在变更日志里留痕 |

**修复后实测结果**：三切片共产出 **143 条淘汰 + 111 条修改**（此前为 0 / 52）。淘汰分布：Java 开发工程师 23 项、后端开发工程师 14 项、数据分析师 9 项、数据仓库工程师 6 项、云计算工程师 1 项、物联网开发工程师 1 项等。

- **Java 开发工程师 23 项**：Struts、J2EE、Hibernate、SpringMVC / Spring MVC、Tomcat、Memcached、SQL Server、Dubbo、Spring Cloud、Oracle、Apache、MyBatis、多线程、Shell、KVM、HTTP、网络编程、分布式系统设计、CSS、HTML、Django、Flask —— 经典 Java 老技术栈集体退场；
- **数据分析师 9 项**：SAS、numpy、scipy、决策树、逻辑回归、聚类算法、聚类分析、神经网络、时间序列算法 —— 传统统计 / 机器学习工具链让位。

> **必须如实说明的一条**：Java 岗 23 项里的 **Django、Flask 属于 2018 语料的聚类污染**——这两个 Python Web 框架在建 2018 基线时被误归入 Java 岗位簇，它们的"淘汰"反映的是历史聚类噪声被新语料修正，**不是真实的技术退场**。我们把它写出来而不是悄悄剔掉：判据是机械执行的，没有为了结果好看做人工挑选；这条噪声也正好指向下一步要改进的岗位聚类精度。

> **判据取舍的诚实交代**：③ 明确**牺牲了一部分召回**——样本薄的岗位一条淘汰都不出。我们认为"漏判"比"错判"代价小得多：一条 Nginx 被判淘汰的假阳性，足以让整套演化结论的可信度归零。

> 验证「既有岗位能力动态更新」闭环：变更项可量化、可溯源、可人工优化，岗位定义随市场数据持续进化。

### 3.6.2 交互式写接口的破坏性防护（2026-07 修订）

演示站上线后，`POST /api/discovery/discover` 与 `POST /api/evolution/update` 被反复点击，暴露出两个交互式写路径的缺陷。评委答辩时必然会点这两个按钮，故一并记录修复：

| # | 缺陷 | 后果（实测） | 修复 |
|---|---|---|---|
| ① | `apply_evolution` 用「本轮聚合出的 active 集合」判淘汰，与 `compute_changes` 的淘汰判据（§3.6.1 四条）**完全脱钩** | 交互式演化只贴几条 JD，旧能力仅靠 history 先验拿到 1 个来源、过不了「≥2 来源」闸门 → 被静默降级；而 `compute_changes` 因先验注入使旧能力仍在 `new_caps` 中，**一条 delete 记录都不写**。实测某岗位 102 行被降级而变更日志 0 条淘汰 | 改为**只降级变更日志判定为 delete 的能力项**，库表与审计轨迹按构造一致。样本不足的交互式演化因此只会新增/修改、不会淘汰——这正是判据③「缺证据不等于反证」的本意，此前只落到了日志侧、没落到写库侧 |
| ② | 发现接口对**已存在**岗位调用 `upsert_job`，而后者会先清空 JobSkill/Evidence 再按传入能力项重建 | 用十来项 LLM 现生成的能力**物理删除**了 301 项交叉验证结果，且 `is_new` 被翻成 True | 已在图谱中的岗位**拒绝落库**，返回定义预览 + 冲突提示（"已在图谱中（v2，37 项已验证能力），未覆盖；如需更新请使用岗位能力演化"）。语义上也成立：已在图谱里的岗位本就不是"新发现" |

**为什么把它写进测试报告**：对一个以"可信、可溯源"为核心卖点的系统，**变更日志与库表事实背离比丢几行数据严重得多**——它意味着审计链本身不可信。修复后二者由同一个判定结果驱动，不存在再次背离的可能。回归测试见 `backend/tests/test_evolution_guards.py`（4 个用例：无 delete 记录时一行都不许降级、只降级日志判定项、新增不受影响、发现接口不得覆盖既有岗位）。

### 3.6.3 溯源与演化的可见性缺陷（2026-07 第二轮修订）

评审反馈「岗位库管理里每个职位点进去，演化历史这一功能还没有实现；溯源证据里标着几处来源但没有具体显示出来」。逐项排查后结论是：**功能都在，坏在三处"数据是对的、页面没说清楚"**。这类缺陷比功能缺失更值得记录——它不会被任何后端测试发现。

| # | 现象 | 实际原因 | 修复 |
|---|---|---|---|
| ① | 溯源证据只看到一排 `87 来源 · 置信 92%` | 证据卡片（平台 / 公司 / 岗位名 / 发布日期 / 可点原始 URL）**渲染代码完整、后端也确实 join 了 `raw_jd`**，但整块包在默认折叠的 `<details>` 里，`<summary>` 又加了 `list-none` 去掉原生三角箭头——**页面上没有任何"这里可以展开"的提示** | 补 `ChevronRight`（`group-open:rotate-90`，纯 CSS）、前 3 条默认展开 |
| ② | "87 来源"展开后只有 6 张卡 | `source_count` 是「提及该技能的 JD 数」，而证据行按上限留存代表样本。两个数字各自都是真的，**撒谎的是把它们混成一个词** | 文案改为 `N 条 JD 提及 · 留存证据 M 条`；留存上限 6 提到 12（`MAX_EVIDENCE_PER_SKILL`）。岗位卡片上的「证据 N」同理改为「JD 支撑 N」 |
| ③ | 新兴岗位点进去演化历史一片空白 | 岗位库按 `is_new` 倒序排列，6 个新兴岗位排最前，**评审点开的第一个岗位必然是空的**。而它们本来就不该有跨切片演化记录——2018 与 2024 历史语料里检索到 0 条 JD | 空态改为**说明视图 + 岗位溯源时间线**：人社部公示日 → 首次可考证出现 → 市场 JD 首次采集到 → 当前 JD 覆盖数，并直接写出「本岗位在 2018 年（0 条）与 2024 年（0 条）历史语料切片中共检索到 0 条 JD」 |

关于 ③ 的判断值得单独说明。技术上完全可以让这 6 个岗位"有"演化历史：保留权威文件定义的 v1，再用 2026 真实 JD 跑一轮得到 v2，diff 即「政策定义 vs 市场实际」。**我们模拟跑过，然后否决了**——该方案会写出事实错误的淘汰记录：`分布式推理` 会从大模型推理优化工程师里被判为"需求消退"，`仿真计算`、`可视化开发` 会从数字孪生里被判退场。这些词本就是大模型从检索摘要里造的、从未在市场数据中出现过，把它们标成"退场"等于断言一段不存在的市场轨迹。**对一个卖反幻觉的系统，审计日志里的假淘汰比页面上少几项能力致命得多。** 改为把"历史语料里检索不到"这个真实事实讲出来——它本身就是「新岗位涌现」最硬的量化证据，且任何人可用一句 SQL 复核。

**另外修复一处自相矛盾**（同一轮复查发现，评审未提及）：`job_to_dict` 返回全部状态的能力项，而前端只分流了 `candidate`、没分流 `deprecated`。后果是 Java 开发工程师 23 项已淘汰能力（Struts / Hibernate / SpringMVC / Memcached / Tomcat / MyBatis…）以**亮色「细分技能点」chip 渲染在 Spring、分布式系统等父项下，和现行技能长得一模一样**。评审在「演化历史」看到「🔴 淘汰 Hibernate」，退回「能力画像」又看到它还在——两个页面互相打脸，而演化叙事正是本作品的核心论据。现改为独立的「已淘汰 N 项（最新窗口 JD 中未再出现）」折叠区、删除线呈现，让"曾经要求、现已退场"这层语义自己说清楚。

**演化路径的溯源补全**：`apply_evolution` 此前只写 `JobSkill`，**从不写 `Evidence`**——交叉验证聚合明明在 `capability["evidence"]` 里给出了带 `raw_jd_id` 的证据，演化路径直接忽略了它。后果是每一条经演化新增/刷新的能力在溯源页都落到「暂无独立JD证据」分支。同时它调 `upsert_skill` 不传 `parent_name`（演化新增的细粒度技能点全部退化成粗粒度，与 3.7.2 的 ② 同一个坑），且不重算 `evidence_count`（岗位卡片数字越跑越旧）。三处一并修复，证据写入抽成 `graph_service.write_evidence()` 由建图与演化两条路径共用、按 `raw_jd_id` 去重，防止再次漂移。修复后全库证据 5386 → **7861 条，且全部可回溯到具体原始 JD**。

回归测试见 `backend/tests/test_rebuild_guards.py`（15 个）与 `test_evolution_guards.py`（8 个）。

### 3.7 置信度校准（说明）

- **统一公式**：C = 0.35·支持率 + 0.20·来源多样性(平台数/3 封顶) + 0.15·时效性(半衰期 180 天) + 0.20·来源权威度(官网/政府 1.0、公开数据集 0.7、网络 0.6) + 0.10·外部验证；五个因子逐项落库（`job_skill.factors`），前端点击置信度徽章可见分解。
- **校准过程**：初版来源多样性上限为 5 平台，在当时仅 3 个采集平台的语料上系统性压低得分；据此将 DIVERSITY_CAP 由 5 调整为 3，并将岗位整体置信度改为**粗粒度 active 能力项的权重加权平均**。该校准做过一次后即**冻结参数**，不做逐岗调参。
- **结果**：全库岗位置信度均值 **0.5513**。
- **提升来源必须说清楚——不是调参**：本轮**公式、五因子权重、多样性封顶值（3）与过滤阈值（0.45）全部原封未动**。均值上升的原因是语料本身：数据源从 3 个渠道扩到 5 类渠道 / 6 个平台批次后，同一技能最多可被 **5 个独立来源**交叉验证（来源池：2018 数据集 / 2024 数据集 / 腾讯 / 网易 / 飞书 ATS / 国聘），"来源多样性"因子更容易达到封顶；同时新增的飞书 ATS（tier=official）与国聘（tier=gov）权威度均为 1.0，把"来源权威度"因子均值一并抬高。即 **证据变厚了，不是分数被调高了**，这正是交叉验证机制"数据越多、判断越可信"的预期表现。

### 3.7.1 细粒度技能点交叉验证补闸（2026-07 修订）

- **问题**：`aggregate_capabilities` 早期对细粒度技能点放行「≥1 个来源即 active」，绕过了粗粒度必须满足的「≥2 独立来源」闸门。后果是 **JD 体量越大的岗位尾巴越长**——大模型算法工程师一度挂到 880 项能力（其中细粒度 834 项、709 项只有 1 个来源），而跑过演化收敛的岗位只有 30-40 项。抽检单来源细粒度，大量是 JD 短语碎片而非技能点（"AI/NLP/代码相关顶会论文"、"Agent项目经验"），以及未归一的同义写法（`Agentic RL` / `Agentic-RL`、`Agent任务编排` / `Agent流程编排`）。
- **判据选择**：对比过三个方案——(A) 仅 ≥2 来源保留 276 项；(B) ≥2 来源且置信度 ≥0.45 保留 201 项；(E) 在 A 基础上再加短语噪声关键词黑名单保留 273 项。**E 比 A 只多删 3 条，却误伤了 `DeepSpeed/Accelerate`、`vLLM/Xinference/Dify` 这类真技能**，说明单来源本身就是噪声的主要载体，不需要脆弱的关键词黑名单。故采用 **A：细粒度技能点与粗粒度必备项同闸，需 ≥2 个独立来源**。
- **处置方式**：**降级为候选（candidate）而非删除**，保留观察与审计链，与演化判据④「降级为候选能力项」口径一致。存量数据由 `data/recalibrate_fine_skills.py` 幂等回填。
- **效果**：岗位-能力关系 active 从 2736 收敛到 920 条，单岗位能力数从 6–880 的悬殊区间收敛到 **6–171**，"一个岗位有 880 项能力要求"这一无法在答辩桌上解释的现象消失。（本轮 6 个新兴岗位改由真实语料重建后，active 增至 **1159 条**，区间仍为 6–171。）
- **颗粒度未被牺牲**：赛题要求"颗粒度到技能点级别"，故 **3257 项候选技能点全部保留在库并可在岗位详情页展开查看**（前端折叠为「候选技能点 N 项（单来源，待交叉验证）」），只是不进入图谱主视图与匹配计算，避免未验证碎片污染。技能树主视图当前呈现 **481 个通过交叉验证的技能点**（其中细粒度 348 个）。

### 3.7.2 新兴岗位改由真实语料重建：一条与主链路脱节的建图路径（2026-07 第二轮修订）

复查线上站时发现：6 个新兴岗位点进去只有 4-6 项"大概念"技能（具身智能工程师 = Python / C++ / 大语言模型 / ROS / PyTorch），而同页面上语料建出来的 AI 产品经理有 14 项粗粒度能力、每项下面挂 10-20 个细分技能点。**同一个系统里两个岗位的颗粒度差了一个数量级**，原因不是数据不够，而是它们走的根本不是同一条建图路径。

**根因（三处叠加，缺一不可）**：

| # | 位置 | 问题 |
|---|---|---|
| ① | `data/seed_new_jobs.py` | 这 6 个岗位由「联网检索证据 + 一次大模型定义」生成，**完全不读 JD 语料** |
| ② | `services/discovery.py` | 该路径的 JSON schema **没有 `parent` 字段**，系统提示还明写「不超过 8 个字、禁止用斜杠/逗号罗列」。而 `graph_service.upsert_skill` 正是靠 `parent` 设 `Skill.parent_id`、`granularity` 再由 `parent_id` 派生——**没有 parent 就在结构上永远是粗粒度**，与提示词写得好不好无关 |
| ③ | `graph_service.upsert_job` | 「先清空 JobSkill/Evidence 再重建」。即使先跑过语料建图，再跑一次 `seed_new_jobs.py` 就会被 4-6 项大模型生成的能力覆盖掉——与 3.6.2 记录的 `/api/discovery/discover` 线上事故同一机制 |

**修复**：这 6 个岗位的真实 JD 其实早已采集入库（智能体 112 条、推理优化 89、具身智能 39、数字孪生 23、生成式测试员 18、数字人 14，共 295 条），且全部命中解析缓存，因此改由主链路 `run_pipeline.py --from-db` 重建**未产生任何新的大模型调用**。为此补了三道护栏：

1. `run_pipeline.py` 新增 `--only-jobs` / `--dry-run` / `--force-rebuild-evolved`。此前"只重建某几个岗位"没有正道，只能全量重跑，而全量重跑会冲掉 15 个已演化岗位的能力项；
2. `graph_service.rebuild_conflict()`：岗位 `version > 1` 或存在任何变更记录时**拒绝重建**并给出冲突说明（形状照抄既有的 `_save_if_absent`）；
3. `upsert_job` 的 `is_new` / `emergence_score` 支持传 `None` 表示"保留库中现值"。此前流水线一律传 `False`，重建一次就把依据人社部文件标注的新兴标记抹平一次。

`seed_new_jobs.py` 也改为：对已在图谱中的岗位默认不再走大模型重定义分支（需显式 `--allow-redefine`），只回补 `is_new` / `emergence_type` / `first_seen_date` 与权威佐证。

**效果**（岗位详情页可逐项核对）：

| 岗位 | 粗粒度必备 | 已验证技能点 | 候选技能点 | 置信度 |
|---|---|---|---|---|
| AI智能体开发工程师 | 5 → **38** | 0 → **87** | 512 | 0.888 → 0.593 |
| 大模型推理优化工程师 | 5 → **33** | 4 → **65** | 499 | 0.967 → 0.567 |
| 具身智能工程师 | 5 → **18** | 0 → **23** | 220 | 0.951 → 0.567 |
| 生成式人工智能系统测试员 | 3 → **15** | 2 | 84 | 0.772 → 0.583 |
| 数字孪生工程技术人员 | 3 → 6 | 2 | 48 | 1.000 → 0.545 |
| 人工智能数字人训练师 | 4 → 5 | 2 | 38 | 0.898 → 0.531 |

具身智能工程师的能力项由此从「Python / C++ / 大语言模型 / ROS / PyTorch」变成 18 项粗粒度能力 + 真实技能点：具身智能下挂 模仿学习 / VLA视觉语言动作模型 / MuJoCo仿真 / 机械臂操作，ROS 下挂 ROS2开发 / Gazebo仿真 / DDS / Cyber RT——这些词全部来自真实 JD 原文并通过 ≥2 独立来源交叉验证。

**两点必须如实说明**：

- **置信度是下降的**（0.77–1.00 → 0.53–0.59），且数字孪生工程技术人员原本是 **1.000**。原因是上一版这 6 个岗位由 `confidence.factors_from_web` 对少量联网检索命中打分，本轮改与既有岗位走同一条 JD 交叉验证链。公式、五因子权重、多样性封顶值与过滤阈值本轮一个都没改（26 个既有岗位均值 0.5483 全程未动，正是旁证）。**一个岗位在能力图谱里拿到 1.000 的置信度，本身就是应该被怀疑的信号。**
- **数字孪生工程技术人员（6 项）与人工智能数字人训练师（5 项）仍然偏薄**，重建没能解决它们。它们是 2026-07 与 2024-08 才公示的新职业，市场 JD 供给本身就少；为它们做的定向补采失败了（详见 2.2 节 `2026W31-r5-dt` 批次记录），我们选择维持现状并写明，而不是靠放宽检索词把邻近岗位混进来凑数。


### 3.8 分级画像评估

- **规模**：**32 / 32 个岗位全部**建有 初/中/高 三档分级画像（`job_level_skill` 共 **1076 条**记录），构档规则：**每档 ≥3 条 JD 且岗位 ≥2 档**才产出，避免小样本档位噪声。上一版有 3 个岗位（人工智能数字人训练师、生成式人工智能系统测试员、数字孪生工程技术人员）未达标——它们的能力集当时来自人社部公示等权威佐证而非 JD 语料聚合，JD 侧无级别信息可分桶；本轮这 6 个新兴岗位改由真实 JD 语料重建（见 3.7.2）后，级别可从 JD 的标题与经验年限推断，三档随之达标。
- **画像与岗位能力集一致性**：分级画像此前是**按级别桶独立重跑聚合**后直接落库，桶内样本小、交叉验证口径与全量建图不同，导致画像里出现岗位能力集里根本没有的技能——实测**越界率 45.5%**（同一岗位，岗位页显示 7 项能力、级别页却列出 88 项，评委点开即是硬伤）。现改为**与岗位 active 能力集取交集**，分级画像只做"级别内的子集划分"、不引入新能力项，当前**越界率 0.0%**（1076 条全部可在岗位能力集中找到对应）。
- **可验证性**：中级→高级晋升 diff 可在线查询（如 AI智能体开发工程师：晋升到高级需新增掌握 云原生 等 8 条能力项）。

### 3.9 已知局限（如实记录）

- **三个时间切片的来源丰富度不对等**：2018 与 2024 两个切片**各自只有单一公开数据集来源**，交叉验证机制在这两个切片上天然拿不到多源支持，因而这两个切片确认下来的能力项数量偏少；2026 切片则有腾讯 / 网易 / 飞书 ATS / 国聘四个独立来源。
- **由此带来的解读警告**：演化变更绝大多数落在 2026 这一步（**493 / 621 条**），**其中一部分来自来源丰富度的提升，而非纯粹的岗位能力增长**。这一点在解读演化曲线时必须打折看待，我们不把它包装成"八年间能力爆发式增长"。
- **淘汰结论同样受语料用词偏好影响**：淘汰判据虽以"最新窗口 JD 原文中一次未出现"为准、可逐条举证，但窗口语料的用词偏好仍会渗入结果——Java 岗 23 项淘汰中的 **Django / Flask 是 2018 语料的聚类污染**被新语料修正，不是真实技术退场（见 3.6.1）。此外，样本薄的窗口按判据③**主动不下淘汰结论**，因此 143 条淘汰是"下限"而非全量。
- **改进方向**：补齐历史年份的多源语料（更多年份的公开数据集、政府平台历史归档），使各切片的来源结构可比，即可把"来源丰富度效应"从真实能力演化中剥离出来。
- **2024 数据集的字段局限**：`dataset_aijob2024` 只有「岗位名 + 技能标签 + JD 正文」，无 company / location / salary 字段（落盘时留空而非臆造），且样本集中在 AI/算法方向、不含 Java/后端/数据分析等传统 IT 岗，因此这些岗位簇仍只有 2018 与 2026 两个观测点。
