# 部署说明

> 智岗图谱（TalentGraph AI）　|　题目 XH-202621
> 在线系统：http://101.200.184.201:8200/

系统采用**后端同端口托管前端静态资源**的一体化方案：一个 FastAPI（uvicorn 单 worker）进程即同时提供 REST API 与前端页面，无需额外 nginx，部署轻量、对小内存服务器友好（实测常驻内存约 162MB）。

---

## 一、环境要求

- Python ≥ 3.11（生产服务器使用 3.12）
- Node ≥ 18（仅前端构建需要，建议本地构建）
- MySQL ≥ 8.0（utf8mb4）
- 可访问：DeepSeek API、BGE 向量服务、Tavily、Serper.dev

---

## 二、方式一：systemd + venv（生产推荐，轻量）

### 1. 本地构建前端

```bash
cd frontend
npm install
npm run build        # 产出 frontend/dist
```

### 2. 打包并上传

```bash
# 将后端 app/、requirements.txt 与 frontend/dist（作为 static）
# 打包上传到服务器 /opt/talent-graph/backend/
#   /opt/talent-graph/backend/app
#   /opt/talent-graph/backend/requirements.txt
#   /opt/talent-graph/backend/static      (= frontend/dist)
# 注意：绝对不要打包本地 .env。服务器保留自己的 .env
#      （DB_NAME=talent_graph_v4、READ_ONLY=1）；用本地文件覆盖会把生产
#      指向错误的库，并把演示站的写接口重新对公网打开。
#   /opt/talent-graph/backend/.env   (服务器上已有，首次部署按第四节手工创建)
```

### 3. 创建虚拟环境并安装依赖（仅预编译 wheel，不在服务器编译）

```bash
cd /opt/talent-graph/backend
python3 -m venv .venv
. .venv/bin/activate
pip install --no-cache-dir --only-binary=:all: -r requirements.txt
```

### 4. 配置并启动 systemd 服务

```bash
cp deploy/talent-graph.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now talent-graph
systemctl status talent-graph
curl http://127.0.0.1:8200/api/health
```

`talent-graph.service` 关键配置（含内存保护）：
```ini
ExecStart=/opt/talent-graph/backend/.venv/bin/uvicorn app.main:app \
    --host 0.0.0.0 --port 8200 --workers 1
# 内存上限，超出自动重启，保护小内存服务器
MemoryMax=420M
CPUQuota=120%
Restart=on-failure
```

### 5. 初始化数据（首次部署，建议本地执行后写入云 MySQL）

真实数据生产链路。**当前生产库是 `talent_graph_v4`；按第五节的发布门禁，下列命令只在影子库上执行**（本地 PowerShell 先 `$env:DB_NAME='talent_graph_v4_shadow'`），验收通过后再提升为发布库。当前生产图谱由 **2570 条真实 JD、5 类渠道 / 6 个 source、15 个采集批次**构建：

```bash
cd backend
# 幂等 schema 迁移（新表 + 新列）
uv run python data/migrate_202609.py --db talent_graph_v4_shadow

# 1) 合法采集（robots+控频+PII 护栏）→ data/raw/{batch}/
uv run python -X utf8 data/collect/run_collect.py \
    --platforms tencent,netease --batch 2026W31-r1 --per-query 12
uv run python -X utf8 data/collect/run_collect.py \
    --platforms feishu_ats,iguopin --batch 2026W31-r2

# 2) 批次 jsonl 入库（URL 去重、级别推断、新一代信息技术领域过滤）
# 腾讯 255 + 网易 251
uv run python -X utf8 data/import_raw.py --batch 2026W31-r1 --tier official
# 飞书 ATS 629（11 家企业官网）
uv run python -X utf8 data/import_raw.py --batch 2026W31-r2 --tier official --filter-it
# 国聘 571（国家级平台）
uv run python -X utf8 data/import_raw.py --batch 2026W31-r2 --tier gov --filter-it
#    历史切片：2018hist-r1（51job2018 公开数据集 300）、
#              2024hist-r1（HuggingFace AI_Job 数据集 300）
#    上述 255/251/629/571 是 r1/r2 初始批次，不是当前 source 总量；
#    含 r3/r4/r5 后当前累计为腾讯 272 / 网易 253 / 飞书 ATS 774 / 国聘 671。

# 先运行 data/backup_jobs.py 留下唯一可恢复备份，再在受控发布窗口执行重建；
# upsert_job 会替换岗位关系/证据
uv run python data/backup_jobs.py
# 用真实 RawJD 构建图谱（生产路径）
uv run python data/run_pipeline.py --from-db

# 3) 三时间切片真实演化（2018 → 2024 → 2026，按时间顺序跑）
#    共产出 621 条变更记录：新增 367 / 淘汰 143 / 修改 111
uv run python -X utf8 data/run_evolution_batch.py --batch-label 2024hist-r1
uv run python -X utf8 data/run_evolution_batch.py --batch-label 2026W31

# 6 个证据背书的新兴岗位 + 权威佐证
uv run python -X utf8 data/seed_new_jobs.py
# 初/中/高分级画像（R6 最终：828 条，覆盖 27/32 岗，越界 0/828）
uv run python -X utf8 data/build_levels.py
# 以下是一轮性历史校准命令，已执行并冻结；新环境不要再次运行
# uv run python data/calibrate_confidence.py                                # 仅保留审计记录
```

（对抗测试夹具路径，仅用于评测基准，不进生产库：`generate_dataset.py` → `run_pipeline.py --reset --use-cache`。）

## 三、方式二：Docker（容器化部署）

提供多阶段 `deploy/Dockerfile`（第一阶段构建前端，第二阶段运行后端并托管静态资源）与 `deploy/docker-compose.yml`（限制 420MB 内存 / 1 CPU）。

```bash
cd talent-graph-system
docker compose -f deploy/docker-compose.yml up -d --build
# 访问 http://<server-ip>:8200/
```

> 注意：在内存 < 2GB 的服务器上构建镜像可能紧张，建议本地构建镜像后 `docker save`/`docker load` 到服务器，或直接采用方式一。

## 四、配置项（backend/.env）

```ini
DB_HOST=...        DB_PORT=...     DB_USER=...   DB_PASSWORD=...   DB_NAME=talent_graph_v4
DEEPSEEK_API_KEY=...    DEEPSEEK_BASE_URL=https://api.deepseek.com   DEEPSEEK_MODEL=deepseek-chat
TAVILY_API_KEY=...      SERPER_API_KEY=...
EMBED_API_KEY=...       EMBED_BASE_URL=http://.../v1   EMBED_MODEL=bge-small-zh-v1.5   EMBED_DIM=512
APP_PORT=8200
READ_ONLY=1        # 公网演示站必须置 1，见下
```

> **只读模式（`READ_ONLY=1`，公网部署必须开启）**：置 1 后，一切**改动知识图谱**的接口统一被 `app/guards.py` 拦下——人工增删改能力项、岗位删除、简历入库直接返回 403；演化推演与新岗位发现降级为 **dry-run**（LLM 与联网检索照常跑完、结果照常返回前端，只是不落库，演示效果与写入版完全一致）；查询、简历解析、人岗匹配、问答助手完全不受影响。前端另据 `/api/health` 的 `read_only` 字段不渲染写入入口，两层各自独立生效。**闸门只设在 HTTP 层**，`data/*.py` 直接调服务层写库、不受影响——发布数据仍走本地脚本，这正是设计意图：公网只读，发布权留在本地。
>
> 开启的理由是两次真实事故：演示站的写按钮对公网零鉴权，2026-07-28 访客点击造成 301 项交叉验证能力被覆盖、313 行静默降级，07-30 又写入 40 条与库表事实不符的变更记录（详见《测试方案与报告》3.6.2 与 3.6.4）。逐个修补写路径只能挡住已知的那一条，故上移为一道总闸。

> **数据库切换与回滚**：当前生产库为 `talent_graph_v4`——它是在 `talent_graph_v3` 的完整克隆上补齐「≥2 个独立雇主实体」闸门后产出的发布库。
>
> | 层级 | 库名 | 说明 |
> |---|---|---|
> | 当前生产 | `talent_graph_v4` | 本轮发布库（补闸后：active 812 / candidate 3604） |
> | 一级回滚 | `talent_graph_v3` | **本轮全程零写入**，切回即恢复到补闸前状态（active 860 / candidate 3556） |
> | 更早回滚 | `talent_graph_v2` | 上一版 806 条语料图谱 |
> | 更早回滚 | `talent_graph` | 最初的演示库 |
>
> 四个库数据均保留未动。切库 = 修改服务器 `.env` 的 `DB_NAME` 后 `systemctl restart talent-graph`，秒级生效、无需改代码。
>
> **数据发布必须走影子库，不得直接改生产库。** 流程为：`data/clone_database_r6.py` 把当前生产库同实例全表克隆为一次性发布候选库（逐表比对行数、列、索引、外键，任一不一致即删除目标库并失败）→ 所有 repair / 重建 / 批算只在影子库上执行 → `data/check_state.py` 只读对账与 `data/release_gate.py` 验收通过后，才改服务器 `.env` 的 `DB_NAME` 切库。切库后原库原封不动保留，即为回滚目标。
>
> 这条规矩不是一开始就有的：第六轮前半段的几次数据修复是「dry-run + `backup_jobs.py` 备份后直接对生产库 apply」，自查认定不合规（备份只覆盖 `job` 维度、演示站在回滚窗口内持续对外服务、验收与生产是同一份数据因而不构成独立证据），后半段才补上上述门禁。详见《改进说明_第三版》文末。

## 五、发布门禁（本轮新增，数据发布必须走这条路）

**规则：任何数据发布都不得直接改生产库。** 修复与重建只在影子库上做，验收通过后才把影子库提升为发布库并切 `DB_NAME`。

```bash
# ① 整库克隆：默认 dry-run，--apply 才动手
#    逐表比对行数 / checksum / 列 / 索引 / 外键 / 表选项，任一不一致即删除目标库并失败；
#    拒绝覆盖已存在的库，且刻意不提供 --force，避免误删其他影子库或回滚库
uv run python -X utf8 data/clone_database_r6.py \
    --source talent_graph_v3 --target talent_graph_v4_shadow --apply

# ② 在影子库上补闸：app/services/repair_safety.py 强制目标库名必须含 shadow，
#    生产库名无条件拒绝；commit 前自检不通过即整体回滚
uv run python -X utf8 data/reconcile_job_skill_state_r6.py --apply

# ③ 重建分级画像（补闸降级后原画像会引用非 active 技能，必须重跑）
uv run python -X utf8 data/build_levels.py

# ④ 全量只读验收：写零、只对账
uv run python data/check_state.py

# ⑤ 验收通过后，把影子库再克隆一份提升为正式发布库
uv run python -X utf8 data/clone_database_r6.py \
    --source talent_graph_v4_shadow --target talent_graph_v4 --apply

# ⑥ 切库：改服务器 .env 的 DB_NAME=talent_graph_v4，然后 systemctl restart talent-graph
```

本轮实际执行时序即上表：`talent_graph_v3` →（克隆）→ `talent_graph_v4_shadow` →（补闸 + 重建画像 + 验收）→（再克隆）→ `talent_graph_v4`。
**中间那个影子库仍然保留，作为审计留存**：任何人都可以拿它和 `talent_graph_v3` 逐表 diff，复核这 48 条降级到底改了什么。

这条流程是被本轮自己的流程违规倒逼出来的——前半段的几次数据修复走的是「dry-run + `backup_jobs.py` 备份后直接对生产库 apply」，
自查认定不合规（备份只覆盖 `job` 维度、演示站在回滚窗口内持续对外服务、验收与生产是同一份数据因而不构成独立证据），后半段才补上上述门禁。
详见《改进说明_第三版》文末。
